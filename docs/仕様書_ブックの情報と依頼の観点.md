# Graft ブックの情報と依頼の観点 仕様書・実装指示（v0.2）

この文書は、`docs/仕様書_VBA連携.md`（v0.3。以下「VBA連携仕様」）の続きとして、次の 4 機能の仕様と実装指示をまとめたものである。実装は `CLAUDE.md` の流儀（日本語コメントで「なぜ」を厚く書く、警告ゼロ、`Graft.Tests` と `Graft.UiTests` の全件成功を確認してから完了報告）に従うこと。コードの名前はファイル名・型名・メソッド名で示し（行番号は書かない）、**「（新設）」と付けたもの以外は、現在のコードに実在する名前**である。

| 記号 | 機能 | 対象 | 一言 |
|---|---|---|---|
| A | ブックの情報 | VBA プロジェクトのみ | シート・テーブル・名前・見出し・参照設定を、コンテキスト収集の項目として AI に渡す |
| B | 依頼の観点 | すべてのプロジェクト（VBA は追記つき） | 「読みやすく」「不具合を直す」などのチップを選ぶと、依頼文に指示が入る |

決定済みの事項（利用者が決めたもの）は本文に断定で書いた。仕様書の作成中に私が決めたこと・迷ったことは付録Aにまとめた。**COM と VBE の挙動は Linux の CI で確かめられない。「実機で要確認」と書いた事項は推測であり、実装者は Windows 実機で確かめてから仕様を確定する（付録B）。**

## 1. 目的と基本方針

### 1.1 目的

- A: AI が「どんなシートや表があるブックか」を知らないまま VBA を書くと、存在しないシート名・列を前提にした回答になる。ブックの構造を、依頼のたびに手で説明しなくて済むようにする。
- B: 依頼の目的（読みやすく、速く、安全に…）を毎回文章で書く手間と、書き方による結果のばらつきをなくす。通常のコードのプロジェクトにも使える。
- C: VBA連携仕様の想定外の上書き（不具合 1・2・6 のような場合）でも、Excel 側の本文を取り戻せるようにする。
- D: 手で直して Excel で試す往復を速くする。

### 1.2 基本方針

- **適用エンジンと履歴の仕組みには手を入れない。** 観点・ブックの情報・控えは、どれも「依頼文を作る側」または「Excel との同期の側」の機能で、`ApplyEngine`、`PathGuard`、`RevisionStore`、`BackupManager`、`RevisionRestorer` は変更しない（VBA連携仕様 1.2・13 と同じ）。
- **COM を呼ぶ部分は Windows 専用**で `Platform/Windows` に閉じ込める。Linux と未対応環境では `Platform/Null` が E706 を返し、A・C・D の UI は出ない。B は COM を使わないので全環境で動く。
- **判定や整形のロジックは `Core/` の純ロジック**に置き、`Graft.Tests` で固める。
- **Excel に繋がらなくても、依頼文の作成は止めない。** A の取得失敗は警告だけで続ける（VBA連携仕様 7.2 の自動 Pull と同じ扱い）。
- **控えは「戻せること」を優先し、掃除は自動の分だけ**にする（利用者の VBE の編集を救う最後の砦は、自動では消さない）。
- **10 万行の編集性能の約束（`tests/Graft.UiTests` の `PerformanceTests`）に影響させない。** エディタの保存経路と `DocumentSession` には触れず、D は保存が終わったあとの通知（後述）から別の経路で動かす。AvaloniaEdit は 11.1.0 のまま。

## 2. 用語

| 用語 | 意味 |
|---|---|
| ブックの情報 | A で Excel から読む、ブックの構造の要約。ミラーにファイルとしては作らない |
| 値の見本 | 各シートの先頭の数行の中身。社外秘が含まれうるため既定オフ |
| 観点 | B のチップ 1 つ。画面の名前（短い）、ツールチップ（一言）、AI に渡す指示文（裏側に持つ）の 3 つ組 |
| 見出し（グループ） | チップをまとめる 5 つ（きれいに／正しく／品質／デザイン／VBA） |
| 共通の決まり | 観点を 1 つでも選ぶと 1 回だけ付く「進め方の決まり」（6.4） |
| 控え | Excel 側の本文を `<データ保存先>/vba-sync/<プロジェクトId>.rescue/` に退避したファイル。VBA連携仕様の「控え」と同じ場所 |
| 世代 | 同じモジュールについての、時刻の違う控え 1 つ |
| 自動控え | C が「Excel へ反映」の直前に毎回残す控え（種別 `auto`。4.4） |
| 自動反映（保存時） | D。保存したモジュールだけを Excel へ送る |

## 4. データモデル

### 4.1 Project への追加

```csharp
// VbaLink に追加（既存の AutoPushAfterApply・SaveWorkbookAfterPush の隣）
public string WorkbookInfoState { get; init; } = "Full";      // "Full" | "StructureOnly" | "Hidden"（ContextFileState と同じ 3 状態）
public bool   WorkbookInfoSampleValues { get; init; }          // 値の見本。既定オフ
public bool   WorkbookInfoIncludeFormulas { get; init; }       // 値の見本に数式も含めるか。既定オフ
public bool   AutoPushOnSave { get; init; }                    // D。既定オフ

// ProjectOverrides に追加（ContextFileStates と同じく、画面で選んだ状態の記憶）
public IReadOnlyList<string> PromptFocusIds { get; init; } = Array.Empty<string>();   // 最後に選んだ観点の Id
```

- いずれも、キーを持たない既存の `projects.json` が読めること（後方互換のテストを書く。JSON は camelCase）。既存の `VbaLink` の他の項目の既定は変えない。
- `WorkbookInfoState` を文字列にするのは、`ProjectOverrides.ContextFileStates` が `ContextFileState` の `Enum.ToString()` を値に持つのと揃えるため。不明な文字列は `Full` として読む。
- `PromptFocusIds` に残った Id のうち、一覧に無いもの（削除された自作の観点）と、VBA でないプロジェクトの VBA 専用の観点は、読み込み時に黙って捨てる。
- **値の見本そのものは、どこにも保存しない**（4.3）。保存するのは「見本を出すか」の選択だけ。

### 4.2 依頼の観点の保存

- 組み込みの観点はコード側（`PromptFocusStore.BuiltIns`）で供給し、書き出さない（`PromptTemplateStore.BuiltIns` と同じ）。
- 自作の観点は `<データ保存先>/focus.json`（`AppPaths.FocusFilePath`。新設）。`JsonFileStore` の復旧つき読み込みを使う（`PromptTemplateStore.LoadAsync` と同じ作法）。`DataDirectory` の `KnownDirectoryPaths` の隣、`TemplatesFilePath` を列挙している箇所に同じ順で `FocusFilePath` を足し、保存先の移行の対象にする。

```csharp
public sealed record PromptFocus   // （新設。Core/PromptFocus）
{
    public required string Id { get; init; }            // 組み込みは "focus-readable" など。自作は "custom-" + Guid
    public required string Group { get; init; }         // "きれいに" | "正しく" | "品質" | "デザイン" | "VBA" | "自分用"
    public required string Name { get; init; }          // チップの短い名前
    public string Tooltip { get; init; } = string.Empty; // 一言の説明
    public required string Body { get; init; }          // AI に渡す指示文（"## 名前" の見出しから始める）
    public string? VbaAddendum { get; init; }           // VBA プロジェクトのときだけ、Body の後ろに足す箇条書き
    public bool VbaOnly { get; init; }                  // VBA プロジェクトのときだけチップに出す
    public bool IsBuiltIn { get; init; }
}
```

```csharp
    string? UsedRange,            // "A1:F120"。空のシートは null

    IReadOnlyList<IReadOnlyList<string>> SampleRows);                // 値の見本。読んでいなければ空
public sealed record VbaTableInfo(string Name, string SheetName, string Range, IReadOnlyList<string> Columns);
public sealed record VbaNamedRangeInfo(string Name, string RefersTo, string? Scope);   // Scope: ブック全体は null、シート限定はシート名
public sealed record VbaReferenceInfo(string Name, string Description, string? FullPath, bool IsBuiltIn, bool IsBroken);
```

- スナップショットは**メモリにだけ**持ち、ディスクへは書かない（値の見本が社外秘を含みうるため。付録A-6）。`ContextCollectViewModel` が最後に成功した 1 件を保持する。

### 4.4 控えのファイル名と種別

控えの置き場は既存のまま `AppPaths.GetVbaRescueDirectory(projectId)`（`vba-sync/<プロジェクトId>.rescue/`）。ファイル名は既存の `VbaRescueNaming.BuildFileName` の形（`<モジュール名>-<yyyyMMdd-HHmmss>.txt`、同じ秒は `_2` と連番）を守り、**種別を接尾辞で表す**。

| 種別（`VbaRescueKind`。新設） | ファイル名 | 残す場面 | 自動の掃除 |
|---|---|---|---|
| `Legacy`（従来） | `Mod-20261121-103000.txt` | 衝突で「Graft 側で上書き」を選んだ直前、書き戻し失敗（E809）。VBA連携仕様 5.5・7.5 | **しない** |
| `Auto` | `Mod-20261121-103000-auto.txt` | 「Excel へ反映」（手動・適用後・取り消し後・D）で Excel を上書きする直前 | する（7.3） |
| `Mirror` | `Mod-20261121-103000-mirror.txt` | 控えをミラーへ戻す直前の、ミラー側の本文 | する（7.3） |

- 解析は `VbaRescueNaming.Parse(fileName)`（新設）が正規表現 `^(?<n>.+?)-(?<d>\d{8}-\d{6})(?:-(?<k>auto|mirror))?(?:_(?<seq>\d+))?\.txt$` で行う。**VBA のモジュール名には `-` が使えない**ので、名前と日時の区切りで一意に切れる。解析できないファイルは一覧に出さず、掃除の対象にもしない（利用者が置いたファイルを消さない）。
- 中身は UTF-8（BOM なし）。モジュール本文を正規化せずそのまま書く（戻したときに行末・空白が変わらないように）。

### 4.5 AppPaths・DataDirectory・Id の付け替え

- `vba-sync/<Id>.rescue/` は既に `VbaSyncDirectory` の配下にあり、保存先の移行・Id の付け替え（`VbaDataRelinker`）の対象である。**C のために追加の移行処理は要らない**（テストで確かめる。11.1）。
- `focus.json` には Id を持つプロジェクト項目が無い。`VbaDataRelinker` の変更は要らない。

## 5. 機能 A: ブックの情報

### 5.1 AI に渡す中身

| 項目 | 内容 | 「構成だけ」 | 「内容も出す」 |
|---|---|---|---|
| シート | 表示名、コード名（`Sheet1` など。ドキュメントモジュールのファイル名と対応する）、表示状態（表示／非表示／VeryHidden）、使用範囲 | ○ | ○ |
| テーブル（ListObject） | テーブル名、シート名、範囲、列名 | ○ | ○ |
| 名前付き範囲 | 名前、参照先、スコープ（ブック全体／シート限定） | ○ | ○ |
| 先頭行の見出し | 各シートの使用範囲の先頭行（最大 `WorkbookInfoMaxColumns` 列） | × | ○ |
| 参照設定 | 名前、説明、パス、組み込みか、参照切れか（**読み取りのみ**） | × | ○ |
| 値の見本 | 各シートの先頭から `WorkbookInfoSampleRows` 行（既定 5）。数式を含めるかは別の選択 | × | **プロジェクトでオンのときだけ**○ |

- 「構成だけ」は、AI に「どのシート・表・名前があるか」だけを知らせたいときの状態。見出し・参照設定・値の見本は出さない。付録A-1 に理由を書いた。
- 先頭行の見出しは「使用範囲の最初の行」であって、テーブルのヘッダー行とは限らない。テーブルがあるシートはテーブルの列名が見出しの役を果たすので、重複は気にしない。
- 隠しシートも含める（表示状態を併記する）。VeryHidden のシートが利用者の意図で隠されている場合があるため、AI に渡ることは UI の注意書きに含める（5.3）。

### 5.2 値の見本（オプトイン）

- **既定はオフ**。プロジェクトごとに `VbaLink.WorkbookInfoSampleValues` をオンにしたときだけ、見本を読む・出す。オフのとき、見本を読む COM 呼び出しは**一切行わない**（取得量を減らし、社外秘を Graft のメモリにも載せない）。
- オンにした瞬間に確認ダイアログを出す（v0.2: 選択ダイアログ `VbaChoiceWindow`。ボタンは「値の見本を渡す」「やめる」で、既定は「やめる」）。文面の骨子: 「各シートの先頭 N 行の値が、依頼文に含まれ、AI に渡ります。個人情報や社外秘が含まれていないか確認してください。」。
- オンの間は、ブックの情報の行に**常時**注意を出す: 「値の見本: オン（各シートの先頭 N 行が AI へ渡ります）」。依頼文コピーのドロップダウンにも同じ注意を 1 行出す。
- 行数は `Vba.WorkbookInfoSampleRows`（既定 5、範囲 1〜20）。数式を含める（`WorkbookInfoIncludeFormulas`）のも既定オフ。数式は参照先のシート名・セル構造を AI に伝えるが、値と同じく中身を含みうる。
- セル内の長い文字列は `Vba.WorkbookInfoMaxCellChars`（既定 60）で `…` つきで切る。1 行あたり `Vba.WorkbookInfoMaxColumns`（既定 30）列まで。

### 5.3 渡し方（コンテキスト収集の項目）

- **ミラーにはファイルを作らない。** コンテキスト収集の画面のファイル一覧（`ContextCollectViewModel.Files`）の先頭付近に、**「ブックの情報」の行**を 1 つ出す。ファイルのノードではなく、専用の行（`VbaWorkbookInfoRowViewModel`。新設）にして、`Files` の選択集計・除外・差分方式の記憶とは混ぜない。VBA プロジェクトのときだけ表示する。
- 既存の 3 状態の操作（クリックで 内容も出す → 構成だけ → 出さない と巡る。`ContextCollectViewModel` の `NextState` と同じ順）で選ぶ。選んだ状態は `VbaLink.WorkbookInfoState` に保存する（`ProjectStore.UpdateAsync`。`PersistFileStatesAsync` と同じ作法）。**既定は「内容も出す」**（5.1 のうち値の見本を除いたものが出る）。
- 行には、取得日時、取得できなかったときの理由、値の見本がオンである注意（5.2）を併記する。「出さない」のときは Excel に問い合わせない。
- **依頼文コピー**: `{{files}}` などと同じ要求（`ContextRequest`）に、ブックの情報の文を載せる（`ContextRequest.WorkbookInfoText`。新設）。テンプレート変数 **`{{workbook}}`** を新設し、展開結果は 5.7 の形（見出し `# ブックの情報` から）。
  - 本文に `{{workbook}}` が無いテンプレートでは、`{{files}}` を自動で足す仕組み（`PromptTemplateRenderer` の `appendFilesIfAbsent`）と同じ考え方で、**「# 対象ファイル」の直前**（観点の文があればその前）に差し込む（6.3 の差し込み規則を共有）。テンプレートの本文そのものは書き換えない。
  - 「出さない」、VBA でない、取得に失敗して前回の成功分も無い、のいずれかのときは何も出さず、見出しだけが残らない。
- **コンテキスト収集の窓のコピー・プレビュー・ファイル保存**（`ContextCollector.CollectAsync`）: 「# 前提」の直後・プロジェクト構成の前に差し込む。窓の出力には「# 対象ファイル」の見出しが無いため。
- トークンの推定（`TokenEstimator`）は、ブックの情報を含めた展開結果で計算する。

### 5.4 取るタイミング

既存の自動 Pull（VBA連携仕様 7.2）と同じ契機で、**Pull の直後**に取る。

- `ContextCollectViewModel.InitializeAsync`／`RefreshAsync` の走査の前（Pull の直後）。
- 依頼文コピーの組み立て（`PromptCopyViewModel` の `RefreshAsync`。走査済みでも、ドロップダウンを開くたびの組み立てで取る）。
- 取得は、`ContextCollectViewModel.PullFromExcelAsync` と並べて `FetchWorkbookInfoAsync`（新設）を呼ぶ。窓口は `MainViewModel.CreateVbaContextPull` と同じ作りで `MainViewModel` が `ContextCollectViewModel` に渡す（`VbaWorkbookInfoFetchAsync` デリゲート。新設）。
- 取得しない条件: VBA プロジェクトでない、`Vba.Enabled` が false、`Vba.CollectWorkbookInfo` が false（9章）、項目の状態が「出さない」。いずれも Excel を呼ばない。
- 同じ組み立ての中で重複して取らない（取得は 1 回の契機につき 1 回。結果は `ContextCollectViewModel` が保持して、テンプレート 1 件ごとの展開では使い回す）。

### 5.5 読み取り（IVbaBridge への追加）

```csharp
/// <summary>ブックの構造（シート・テーブル・名前・見出し・参照設定。options で値の見本）を読む。書き込みはしない。</summary>
Task<GraftResult<VbaWorkbookInfoSnapshot>> ReadWorkbookInfoAsync(
    string workbookFullName, VbaWorkbookInfoOptions options, CancellationToken ct = default);
```

- `NullVbaBridge` は E706。`FakeVbaBridge` には、返すスナップショット、失敗させる `GraftIssue`、遅延、呼び出し回数と最後に受け取った `options`（値の見本を読まなかったことを確かめる）の口を足す。
- **読み方（`WindowsVbaBridge.Info.cs`）**。`StaWorker` の 1 呼び出しの中で、シート単位に一括で読む。セルを 1 つずつ読まない。
  1. ブックを引く（VBA連携仕様 5.2 の ROT。見つからなければ E804）。
  2. `Worksheets` を列挙する（グラフシートは対象外）。シートごとに、`Name`・`CodeName`・`Visible` と、`UsedRange` の `Row`・`Column`・`Rows.Count`・`Columns.Count`・`Address(False, False)` を取る。空のシート（`UsedRange` が A1 だけで `Value2` が `Empty`）は使用範囲 null とする。
  3. 見出し行: 使用範囲の先頭行を `MaxColumns` 列まで、**`Range(...).Value2` を 1 回**で読み、2 次元配列（`object[,]`、下限 1）を受ける。1 セルだけのときは配列ではなくスカラーが返るので、両方を扱う。
  4. 値の見本（`SampleRows > 0` のときだけ）: 先頭行の次から `SampleRows` 行、同じ列幅を `Value2` で 1 回読む。数式を含める指示のときは、同じ範囲の `Formula` も 1 回読み、`=` で始まるセルは `=式 → 値` の形にする。
  5. `ListObjects` を列挙し、`Name`・`Range.Address`・`HeaderRowRange.Value2`（列名を 1 回で）。`Names` を列挙し、`Name`・`RefersTo`・`Parent`（シート限定か）。`_xlnm.*`（印刷範囲など）と `_FilterDatabase` は除く。
  6. 参照設定（`IncludeReferences` のとき）: `VBProject.References` の `Name`・`Description`・`FullPath`・`BuiltIn`・`IsBroken`。**`Workbook.VBProject` に触れない（E802）ときは参照設定だけを省き**、`Omitted` に理由を残す。シート・テーブル・名前は `VBProject` に依存しないので読める。ロック中（E803）でも `References` は読めない見込みなので同様に省く（実機で要確認）。
- **`VbaCellText.Render(object? value2, int maxChars)`**（`Core/Vba`。純ロジック）がセルの値を文字列にする: `Empty`/null → 空、`string` → 改行・タブを空白 1 つに畳んで `maxChars` で切る、数値 → 不変カルチャで、真偽値 → `TRUE`/`FALSE`、**エラー値（`Value2` では HRESULT に近い負の整数で返る）→ `#N/A` 等の名前**（`-2146826246` → `#N/A`、`-2146826281` → `#DIV/0!`、`-2146826273` → `#VALUE!`、`-2146826265` → `#REF!`、`-2146826259` → `#NAME?`、`-2146826252` → `#NUM!`、`-2146826288` → `#NULL!`。値は実機で確かめる。付録B）。日付は `Value2` では日付の連番（`double`）になり、日付かどうかは表示形式を読まないと分からない。**この版では連番のまま出し、日付の判別はしない**（表示形式の取得は COM 呼び出しが増えるため。付録A-7）。
- **上限**（`options` と設定。9章）:

| 対象 | 上限 | 超えたとき |
|---|---|---|
| シート数 | `MaxSheets`（100） | 先頭から 100 枚。残りは「他 N 枚」と `Omitted` |
| 見出し・見本の列数 | `Vba.WorkbookInfoMaxColumns`（30） | 右を切り、`…`（他 N 列） |
| 見本の行数 | `Vba.WorkbookInfoSampleRows`（5） | それ以上は読まない |
| セルの文字数 | `Vba.WorkbookInfoMaxCellChars`（60） | `…` つきで切る |
| テーブル数／1 表の列名数 | 100／60 | 超過分を省く |
| 名前付き範囲 | 200 | 超過分を省く |
| 参照設定 | 100 | 超過分を省く |
| 出力全体の文字数 | `Vba.WorkbookInfoMaxChars`（20000） | `VbaWorkbookInfoFormatter` が末尾から切る。切る順は **値の見本 → 見出し → 参照設定 → 名前付き範囲 → テーブルの列名 → シート**（構成ほど後まで残す）。切ったら末尾に「（長いため一部を省略しました）」 |

- **時間切れ**: 呼び出し全体は既存の `Vba.CallTimeoutMs`（既定 30 秒）に従う（5.3 のスレッドの捨て方も同じ）。それとは別に、ブリッジはシートの合間に `options.Budget`（`CallTimeoutMs` の 2/3）を見て、**超えていたらそこまで読めた分を返し**、`Omitted` に「時間がかかったため、シート X 以降は読めていません」を残す。モジュールの書き込みと違い、途中までの結果に危険は無いため。1 呼び出しが戻らない（マクロ実行中・モーダル表示中）場合は、全体の時間切れで E805。
- **E813 は使わない。** 読み取りは `VBProject.Mode`（デザインモード）を要求しない。マクロの実行中に Excel が呼び出しを拒否したら、`ComRetry` の再試行のあと E805。

### 5.6 失敗時の扱い（収集を止めない）

| 状況 | 結果 | 依頼文・収集 |
|---|---|---|
| ブックが開いていない（E804）、Excel が応答しない（E805）、通信の失敗（E801）、保護ビュー・ロック等の利用不可 | 取得を諦める | 前回成功した分が同じセッション内にあれば、**それを使い**、見出しの行に「（取得日時: …。最新を読めていません）」を添える。無ければ何も出さない。どちらも警告を 1 件出す |
| 一部だけ読めた（参照設定のみ E802、時間切れ、上限） | 読めた分を使う | `Omitted` を E815（警告）にして出す |
| すべて読めた | — | 警告なし |

- 警告の出し先は、自動 Pull の警告と同じ（コンテキスト収集の窓ではステータス欄 `StatusMessage`、依頼文コピーではドロップダウンの状況欄）。Pull の警告と同時に出るときは 1 行に連結する。
- 値の見本の確認ダイアログ（5.2）以外に、ブックの情報の取得でダイアログを出さない（衝突ダイアログのようなものは無い）。

### 6.2 画面

- **置き場所は 2 か所**: 依頼文コピーのドロップダウン（`PromptCopyViewModel` の画面）と、コンテキスト収集の窓。どちらも同じ `PromptFocusPanel`（新設）を置き、**同じ選択状態**（`ContextCollectViewModel.Focus`。`PromptFocusSelectionViewModel`）を共有する。片方で選べば、もう片方にも反映される（`Context` を両者が共有しているのと同じ）。
- 5 つの見出しごとにチップを折り返しで**最初からすべて並べる**（折りたたまない）。チップは `ToggleButton` 相当で、複数選べる。VBA の見出しは VBA プロジェクトのときだけ出す。自作の観点があれば末尾に「自分用」の見出しを出す。
- チップにマウスを乗せると一言の説明を出す（`HelpTip.Standard`／`Detailed` の作法。`SettingsHelpTipCoverageTests` の「操作可能なコントロールに HelpTip が付いている」検査に通すこと）。AI に渡す指示文は画面に出さない。読み上げ用の名前は「チップ名（選択中／未選択）」。
- パネルの見出しに、選択数（「依頼の観点 3」）と「すべて解除」のボタンを置く。
- チップを切り替えたら、依頼文コピーのトークン推定を再計算する（「選んだファイルも付ける」の切り替えと同じ `RefreshAsync(keepSelection: true)`。1 回の計算では同じ選択で通す）。
- **最後の選択はプロジェクトごとに記憶**する（`ProjectOverrides.PromptFocusIds`）。プロジェクトを開き直したとき、前回の選択を復元する。保存は選択が変わってから 500ms 後にまとめて 1 回（`ProjectStore.UpdateAsync`。古いスナップショットで丸ごと上書きしない）。

### 6.3 展開の規則

- 新しいテンプレート変数 **`{{focus}}`**（展開結果は 6.4 の形）。**何も選ばれていなければ空**で、前後の空行を詰めて痕跡を残さない。
- `{{focus}}` を含まないテンプレートで 1 つ以上選んだ場合は、次の順で差し込み位置を決める（`{{files}}` の自動付加と同じ考え方。テンプレートの本文そのものは書き換えない）。
  1. テンプレート本文の「`# 対象ファイル`」だけの行の**直前**。
  2. 無ければ、`{{files}}` を含む行の直前。
  3. 無ければ、ファイル部分が自動付加されるとき（`appendFilesIfAbsent`）は、付加する「# 対象ファイル」の直前。
  4. 付加するファイルも無いときは、末尾。
- `{{workbook}}`（5.3）があるときは、その**直後**に置く（v0.2。前提 → ブックの情報 → 観点 → 対象ファイル の順を守るため。冒頭の変更点の表）。
- **展開の実装上の約束**: 観点とブックの情報の文は、ほかの変数（`{{tree}}`・`{{files}}`・`{{standingContext}}` など）の展開が**済んだあと**に差し込む。本文中の `{{focus}}` を先に私用領域の文字のマーカーへ置き換えておき、最後にマーカーを文に置き換える。理由は 2 つ: ファイルの中身に `{{focus}}` という文字列があっても置換されないこと、自作の観点の文に `{{files}}` と書かれていても再展開されないこと。
- コンテキスト収集の窓のコピー・プレビュー（`ContextCollector.CollectAsync`）では、「# 前提」の直後に、ブックの情報 → 観点の順で差し込む（`ContextRequest.FocusText`。新設）。
- 画面の並び順で連結する（クリックした順ではない）。同じ選択なら、いつも同じ依頼文になる。

## 7. 機能 C: 反映前の自動控え

### 7.1 何をするか

「Excel へ反映」で Excel 側が上書きされる**直前**に、上書きされる各モジュールの Excel 側の本文を、毎回 `.rescue/` に世代つきで残す。残す場面は `VbaSyncService.PushCoreAsync` を通るすべての反映（手動の「Excel へ反映」、適用後の自動 Push、取り消し・復元後の Push、衝突の「Graft 側で上書き」、D の保存時の自動反映）。

### 7.2 控えを残す手順（`PushCoreAsync`）

1. 書き込みの対象（`writes`）のうち、**既存のモジュールを上書きするもの**（`VbaSyncAction.Push`）が対象。`PushCreate`（Excel に無い新規）は残す本文が無いので対象外。
2. **衝突の上書き（`VbaSyncAction.Conflict` の「Graft 側で上書き」）は、従来どおり `KeepRescueCopyAsync` が `Legacy` の控えを残す**ので、自動控えは重ねて作らない。
3. 控えの本文は、`BuildPlanAsync` が既に読んでいる `work.Excel[相対パス].Code` を使う（**追加の COM 呼び出しはしない**）。
4. 同じモジュールの最新の `Auto` の控えと本文のハッシュ（`VbaTextNormalizer.Hash`）が同じなら、書かない（同じ内容の世代が積み上がらないように）。
5. `<モジュール名>-<yyyyMMdd-HHmmss>-auto.txt` を書く（4.4。同じ秒は連番）。時刻は `VbaSyncService` の `_clock`。
6. **全モジュールの控えを書き終えてから** `WriteComponentsAsync` を呼ぶ。
7. 控えを書けなかったとき（ディスクの空き不足など）: **反映は止めず**、そのモジュールには E816（警告）を出して続ける。理由は、通常の反映では Excel 側の本文は直前の同期の内容と同じであることがほとんどで（変わっていれば衝突として別に止まる）、控えを書けないだけで利用者の作業を止めるのは釣り合わないため。衝突の上書きだけは従来どおり、控えを書けなければ上書きしない（失われるのが利用者の VBE の編集だから）。
8. 控えを書いたあと、掃除（7.3）を呼ぶ。掃除の失敗は反映の結果に影響させず、ログ（`Logger`）に警告として残す。

### 7.3 世代数・容量の上限と掃除

| 規則 | 値 | 設定 |
|---|---|---|
| 1 モジュールあたりの `Auto`＋`Mirror` の世代数 | 20 | `Vba.RescueMaxGenerations`（範囲 1〜200） |
| 1 プロジェクトの控え全体の容量 | 50 MB | `Vba.RescueMaxTotalMB`（範囲 5〜1000） |

`VbaRescuePruner.Plan(entries, maxGenerations, maxTotalBytes)`（新設。純ロジック）が、消すファイルの一覧を返す。

1. モジュールごとに、`Auto` と `Mirror` を新しい順に並べ、`maxGenerations` を超えた古い方を消す。
2. 全体（`Legacy` を含む）の合計が `maxTotalBytes` を超えるなら、`Auto` と `Mirror` を**古い順**に、合計が収まるまで消す。
3. **`Legacy` は自動では消さない**（容量の計算には入れる）。`Legacy` だけで上限を超えたときは、何も消さずに一覧の画面で警告する。
4. **各モジュールの最新の `Auto` 1 件は、容量を理由に消さない**（容量が小さすぎる設定でも直近の控えは残す）。
5. 掃除は、控えを書いた直後と、「Excel 側の控えを見る」を開いたときに行う。起動時や定期の掃除はしない。実際の削除は `ITrashService` ではなく通常の削除（控えを消すだけで、利用者の作成物ではないため）。削除に失敗したファイルは次回に回す。
6. プロジェクトを削除しても、控えは消さない（既存の `ProjectStore.RemoveAsync` の扱いのまま。Excel 側から失われた本文を含みうる）。

### 7.4 一覧・差分・戻す

- 入口: プロジェクトの右クリック「**Excel 側の控えを見る…**」（VBA プロジェクトのときだけ）とコマンドパレット。ファイルを見るだけなので、Excel が開いていなくても、`Vba.Enabled` が false でも開ける（戻すのは 7.5）。
- `VbaRescueWindow`（新設）: 左にモジュールごとの控えの一覧（日時、種別〔「反映前の自動控え」「上書き前」「戻す前のミラー」。`Legacy` は E809 の書き戻し失敗も同じ表示〕、行数、サイズ）、右に**選んだ控えと現在のミラーの差分**。差分は `DiffViewModel`（左右比較）で、`VbaConflictDiff` と同じく 2 つの本文から `BlockPlan` を作る。
- ボタン: 「**ミラーへ戻す**」「控えを削除」「保存先を開く」。
- 履歴（リビジョン）とは混ぜない（付録A-8）。戻した結果は履歴に記録されず、`Logger` に `vba-rescue` として残す。

### 7.5 戻す: ミラーに取り込む形にする

「戻す」は、**控えの本文をミラーのファイルへ書く**（Excel には書かない）。その後、ミラーは「未反映」（`VbaSyncAction.Push`）になり、戻した内容は利用者が「Excel へ反映」で送る。

1. 対象のミラーのファイルに**未保存のタブ**があれば、Pull と同じ確認（`BeforeApplyAsync` と同じ保存確認）を出す。断られたら戻さない。
2. 現在のミラーの本文が控えと違うなら、その本文を `Mirror` の控え（`-mirror.txt`）として先に残す。**これを残せなければ、戻さない**（E816）。
3. ミラーのファイルに書く（`FileTextIO.WriteAsync`。既存のファイルは `TextShape` を保ち、無ければ UTF-8・BOM なし・CRLF）。**同期基準（`VbaSyncStateStore`）は触らない**。ミラーだけが変わるので、`VbaSyncPlanner` が自然に「未反映」と判定する。ミラーのファイルが無い（削除保留の）モジュールなら、ファイルが再び現れて削除保留が解除される。
4. 書いたあと、ステータスに「戻しました。履歴には記録されません。Excel に送るには『Excel へ反映』を押してください」と出し、「今すぐ Excel へ反映」のボタンを添える（押すと、そのモジュールだけ `PushAsync`。Excel 側が変わっていれば衝突ダイアログ）。
5. エディタで開いているタブは、既存の `FileWatchService` の仕組みで再読込される（VBA連携仕様 7.2）。
6. **Excel へ直接書く形にしない理由**: 直接書くには、E813（実行中）・CP932・衝突検査・同期基準の更新といった Push の安全装置を別の経路で作り直す必要がある。ミラーを経由すれば、すべて既存の Push が担う（付録A-4）。

## 8. 機能 D: 保存時の自動反映

### 8.1 動作と既定

- `VbaLink.AutoPushOnSave`（既定 **false**）。プロジェクトの右クリックのチェック項目「**保存したらそのモジュールを Excel へ反映する**」で切り替える（`AutoPushAfterApply`・`SaveWorkbookAfterPush` と同じ並び。`Vba.Enabled` が false のときは無効）。
- オンのとき、エディタで **VBA のミラー内の同期対象のモジュール**を保存すると、そのモジュールだけを Excel へ送る。

### 8.2 契機: 保存の通知から、別の経路で動かす

- **`DocumentSession` と保存経路には触れない。** 契機は、保存が成功したあとに `EditorPaneViewModel` が上げる `TabSaved`（`SaveActiveAsync`・`SaveAllAsync` の成功後）。`MainViewModel`（新ファイル `MainViewModel.VbaSaveSync.cs`）がこれを購読する。
- ハンドラが**同期で行う仕事は、条件の判定とキューへの追加だけ**（数マイクロ秒）にする: 現在のプロジェクトが VBA でアクティブ（`IsVbaActive`）、`AutoPushOnSave` がオン、保存したファイルがミラーの中、`VbaMirrorLayout.TryParse` が成功する同期対象、適用中（`IsApplyInProgress`）でない。条件を満たしたら `VbaSaveCoalescer`（8.3）に相対パスを渡して**すぐ戻る**。ファイルの読み込み・ハッシュ・COM は、すべてキューの先の非同期の処理で行う。
- 保存した瞬間に適用中のときは何もしない（適用後の Push が、Push 判定のモジュールも同梱する。VBA連携仕様 7.2b）。
- 保存の通知からキューに入ったあと、送る時点（静かになってから）で適用中、または取り消し・復元の後の反映の最中（`_isVbaPushing`）なら、終わってから送る（溜め直して、もう一度静かになるのを待つ）。手動の「Excel へ反映」の最中（`IsWritingToExcel`）は、`VbaSyncService` のゲートで順番に並ぶので、ここでは止めない。
- 経路の対象外（付録A-9）: タブを閉じるときの保存、適用前の保存確認（`SaveFilesAsync`）、エクスプローラー経由の変更。これらは通常どおり「未反映」のバッジに残り、手動の「Excel へ反映」か次の保存で送る。

### 8.3 まとめ・間引き（`VbaSaveCoalescer`。純ロジック）

- 同じモジュールの保存が続いたとき（`SaveAllAsync` や連続保存）は、**最後の通知から 500ms 静かになったら 1 回**だけ送る。複数のモジュールが溜まったら、1 回の `PushAsync(project, only: 溜まった相対パス)` にまとめる。
- 反映の最中に来た保存は、終わったあとに続けて 1 回処理する（同時に 2 つ走らせない。`VbaSyncService` の `_gate` による直列化にも任せる）。
- 時刻はテストで差し替えられるよう、時計と遅延を注入する。
- 実装: `VbaSaveCoalescer(flush, quiet, clock, delay, onError)`（`Core/Vba`）。`Add(projectId, relativePath)` は表を更新するだけですぐ戻る。送信（`flush`）は 1 つのポンプだけが呼ぶので重ならず、`flush` が false を返したら「いまは送れない」として溜め直す。例外は `onError` に渡して次へ進む（ポンプが止まって以後の保存が送られなくなるのを避ける）。ポンプは最初の `Add` を呼んだ同期コンテキスト（UI スレッド）で始まり、送信の続きもそこへ戻る。

### 8.4 1 モジュールだけを読む（性能と Excel の負荷）

現在の `VbaSyncService.BuildPlanAsync` は、`only` で対象を絞っても、Excel の**全モジュールを読み**（`ReadComponentsAsync(…, null, …)`）、ミラーの**全ファイルを読む**（`ReadMirrorAsync`）。保存のたびにこれを行うと、大きなブック（約 100 モジュール）では Excel を数秒占有し、利用者の操作を妨げる。そこで、**対象を絞った読み取りを新設**する。

- `BuildPlanAsync` に「名前で絞る」引数を足し、`scope` があるときは `ReadComponentsAsync(workbook, names: 対象のコンポーネント名)` と、対象のミラーファイルだけの読み取りにする（`IVbaBridge.ReadComponentsAsync` は既に `names` を受ける）。`scope` が null のときの動作は変えない。
- 絞ったときの計画は、対象のモジュールの判定だけを返す（`VbaSyncPlanner` の判定表はそのまま）。削除保留や記録の破棄など、全体を見ないと出せない判定は、絞った読み取りでは行わない。
- 手動の「Excel へ反映」・適用後の Push は従来どおり全体を読む。**絞る読み取りは D だけが使う**（手動の Push に影響させない）。
- 実装: `VbaSyncService.PushSavedAsync(project, savedPaths)`（D 専用。`IsWritingToExcel` の旗も立てる）→ `PushCoreAsync(narrowRead: true)` → `BuildPlanAsync(narrowRead: true)`。Excel は対象のコンポーネント名だけを `ReadComponentsAsync(names)` で読み、ミラーは対象のファイルだけ読む（ディレクトリを走査しない。対象外のファイルへの E810 は出さない）。計画の入力（ミラー・Excel・同期状態）を対象に絞る既存の仕組みのおかげで、対象外のモジュールの記録を破棄したり、削除保留の印を付けたりしない。
- 反映前の自動控え（7章）の掃除は、D では 30 秒に 1 回に間引く（保存のたびに控えのフォルダを走査・削除しないため。上限は目安なので数十秒のあいだ少し超えても実害が無く、超過分は次の掃除でまとめて消える。手動の反映は従来どおり毎回掃除する）。

### 8.5 衝突・エラーの扱い（作業を止めない）

- **ダイアログを出さない。** 保存のたびに割り込まないため。
- 衝突（`VbaSyncAction.Conflict`）: **送らない**。その場でバッジの印だけ付ける（**通知は出さない**。保存のたびに割り込まないため）。`VbaBadgeLogic` に「保存時の自動反映をしなかった衝突 N」を足し（メモリだけ。起動をまたいで残さない）、名前の下の補足行とツールチップに出す。手動の「Excel へ反映」の衝突ダイアログ（VBA連携仕様 7.5）で解決する。次に同じモジュールが衝突なしで反映できたら印を消す。手動の取込・反映で衝突を解決した（または衝突でなくなった）モジュールの印も消す（`ProjectPaneViewModel.MarkVbaSaveConflicts`・`ClearVbaSaveConflicts`。メモリだけ）。
- E805（応答しない）、E813（マクロの実行中・中断中）、E804（ブックが開いていない）、E801、E811（CP932）、E808: **通知だけ**（ステータスバーの数秒で消える通知。`ShowApplyUndoNotice` と同じ作法）。内容は「保存しました。Excel への自動反映は行いませんでした（E813: マクロの実行中です）」の形で E817（警告）の見出しを使う。ファイルは保存済みで「未反映」のまま残る。
- 通知の理由は、ステータスバーの幅（約 460px。全角で 40 文字ほど）で末尾が省略されないよう、エラーの見出しをそのまま使わず短い言い回しにする（`VbaSaveNoticeThrottle.ShortReason`。例: E813「マクロの実行中です」、E805「Excel が応答しません」、E804「ブックが開いていません」）。ステータスバーの通知にはツールチップで全文も出す。
- 通知は**同じコードなら 60 秒に 1 回**までに間引く（`VbaSaveNoticeThrottle`）（連続保存で通知が積み上がらないように。E811 は文字コードの問題が直るまで毎回出るので、モジュール名つきで 1 回に絞る）。
- 自動で再試行しない（マクロ実行中などに保存のたびにタイマーで叩き続けない）。次の保存か手動の反映で送る。
- 成功したら通知は出さず、プロジェクトペインのバッジの件数（未反映）が減るだけにする。`SaveWorkbookAfterPush` がオンなら、自動反映のあとにブックも保存する（読み取り専用なら E807。通知）。
- 反映の前に、7章の自動控えが働く（同じ `PushCoreAsync` を通るため）。

### 8.6 10 万行の性能の約束への影響

- 保存経路（`DocumentSession.SaveAsync`）、`EditorPaneViewModel.SaveActiveAsync`・`SaveAllAsync` のコードは変えない。`TabSaved` の購読者が 1 つ増えるだけで、ハンドラは 8.2 のとおり即座に戻る。
- VBA でないプロジェクト、`AutoPushOnSave` がオフのプロジェクトでは、ハンドラは最初の条件判定で戻る。

## 14. 実装時の注意（まとめ）
