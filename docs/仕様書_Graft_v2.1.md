# Graft — 仕様書 v2.1

プロジェクト管理を中核に、コードエディタと、対話型AIが出力したコードの安全な「接ぎ木」を統合した**クロスプラットフォーム**デスクトップ開発ツール。

> **実装者へ**: 本仕様書は実装の唯一の基準である。着手前に**附録A（実装者向け指示）**を必読のこと。v2.0 からの変更点は**附録B**にまとめる。v1.5〜v2.0 で実装済みの資産（パーサ・マッチング・適用・リビジョン・エディタ・エクスプローラ等）は捨てずに再利用する。

---

## 0. v2.1 改訂の背景

v2.0 は WPF による Windows 専用アプリだった。v2.1 では **Windows と Linux の両方で動作する**ことを要件に加える。

### 0.1 変更の動機

第一に、**Linux でも使いたい**という要求そのもの。

第二に、**開発中の品質検証が根本的に改善する**こと。WPF は Windows 実機でしか実行できず、ビルドが通っても起動時に落ちる種類の不具合（リソースの型不一致、`StaticResource` の解決失敗、コントロールテンプレートの表示崩れ）を自動検証できなかった。実際 v2.0 の開発では、これらを人手による実機確認でしか発見できなかった。

Avalonia は **headless モードで実際に描画し、フレームを画像として取得できる**。これにより以下が自動テストとして成立する。

- 画面を実際に描画し、レイアウト崩れ・リソース解決失敗を検出する
- ボタンのクリック、キーボード入力（日本語IMEを含まない直接入力）を再現し、操作シナリオを検証する
- スクリーンショットを保存して目視確認・回帰比較に使う

**この検証能力は品質要件そのものとして扱う**（18章・附録A.7）。

### 0.2 対応プラットフォーム

| OS | 位置づけ |
|---|---|
| Windows 10 (21H2以降) / 11、x64 | **正式対応**。全機能が動作する |
| Linux（x64、glibc ベースの主要ディストリビューション） | **正式対応**。一部のOS統合機能に制限あり（2.3） |
| macOS | 対象外。Avalonia の性質上おそらく動作するが、検証も保証もしない |

## 1. 概要

### 1.1 設計目標

v2.0 の5目標を維持し、1つ追加する。

1. **プロジェクト管理を中核とする。**
2. **一般的なコードエディタの機能を市販ソフト水準で備える。**
3. **トークン消費の最小化。** search/replace形式を第一級の入力として扱う。
4. **変更の追跡可能性。** 適用単位をリビジョンとして記録する。
5. **製品相当の完成度。** UI・エラー処理・異常系からの復帰を市販ソフトの水準で作り込む。
6. **（新規）プラットフォーム差を機能ではなく実装の詳細に留める。** OS固有機能は抽象化の背後に隠し、利用できない環境では機能を欠くのではなく**縮退した代替**を提供する。落ちたり無言で無視したりしない。

### 1.2 用語定義

v2.0 の用語を維持し、以下を追加する。

| 用語 | 定義 |
|---|---|
| プラットフォームサービス | OS固有機能（トレイ・ホットキー・クリップボード監視・ごみ箱・テーマ判定等）の抽象インターフェース群 |
| headless テスト | 画面表示なしにUIを構築・操作・描画して検証する自動テスト |

## 2. 動作環境・配布形態

### 2.1 フレームワークとランタイム

- フレームワーク: .NET 8 / **Avalonia UI 11**
- 実行形態: self-contained、**単一ファイル形式**（`PublishSingleFile`。ネイティブライブラリの
  自己展開は行わない、`IncludeNativeLibrariesForSelfExtract=false`）。RID ごとに生成する
  - Windows: `win-x64` → `publish/win/Graft.exe` ＋ネイティブDLL3つ（計4ファイル）
  - Linux: `linux-x64` → `publish/linux/Graft` ＋ネイティブDLL3つ（計4ファイル）
  - 発行物はこの4ファイルをまとめて配布する。実行ファイルだけを取り出すと
    `FileNotFoundException` で起動できない（18章・20.1・附録B）
- ランタイム事前導入・インストーラ・管理者権限: いずれも不要
- レジストリ書き込み: 行わない（Windows でのテーマ判定等の**読み取り**のみ許可）
- ネットワーク通信: **自動更新の確認・ダウンロードのときだけ**、GitHub Releases API
  （既定 `https://api.github.com/repos/Yu5rin/Graft/releases/latest`。設定画面で変更可）へ
  HTTPS通信する。発生する条件は「利用者がGraftを起動するたびに1回（ただしGraft自身の
  自己再起動では発生しない）」または「設定画面の『今すぐ更新を確認』を押したとき」の
  いずれかに限る（15.1章）。それ以外の外部通信（使用状況の送信・テーマのダウンロード等）は
  引き続き一切行わない

### 2.3 プラットフォーム別の機能対応

**「未対応」は許容しない。必ず縮退した代替を用意し、利用できない旨をUIに明示する。**

| 機能 | Windows | Linux | Linux での実装方針 |
|---|---|---|---|
| エディタ・エクスプローラ・接ぎ木・履歴・設定 | 対応 | 対応 | 差異なし |
| Shift_JIS の読み書き | 対応 | 対応 | `CodePages` はクロスプラットフォーム |
| 長いパス（MAX_PATH 超過） | `\\?\` 前置 | 該当なし | Linux にパス長の実用上限がないため何もしない |
| 安全な書き込み | `File.Replace` | `File.Move(overwrite)` | 既存の分岐を維持 |
| 多重起動の防止 | 名前付き Mutex | 名前付き Mutex（**`Global\` プレフィックス必須**） | 実装は Windows・Linux 共通（`Core/SingleInstanceGuard.cs`）。理由・判定不能時の縮退・発行フォルダ単位での判定は本節末尾の説明を参照 |
| ごみ箱への削除 | `SHFileOperation` | **XDG Trash 仕様**（`~/.local/share/Trash`） | 実装できない場合は確認ダイアログのうえ通常削除。無言で消さない |
| ファイルマネージャで表示 | `explorer.exe /select,` | `xdg-open`（親フォルダを開く） | ファイル選択までは保証しない |
| トレイ常駐 | `Shell_NotifyIcon` | **`StatusNotifierItem`（D-Bus）** | 利用不可のデスクトップ環境では**トレイ機能を無効化し、その旨を設定画面に表示**する |
| グローバルホットキー | `RegisterHotKey` | **X11 は `XGrabKey`、Wayland は利用不可** | 利用不可の場合は `E601` として通知し、アプリ内ホットキーのみで動作を継続する |
| クリップボード監視 | `AddClipboardFormatListener` | **X11 は `XFixes` によるセレクション監視、Wayland は利用不可** | 利用不可の場合は `E602` として通知。手動での取り込み（`Ctrl+Shift+V`）は常に使える |
| システムテーマの追従 | レジストリ読み取り | **`org.freedesktop.appearance color-scheme`（XDG Desktop Portal）** | 判定できない場合はダークへフォールバック |

**Wayland では OS の設計上グローバルホットキーとクリップボード監視が実現できない。** これは制限として明示し、代替手段（アプリ内ホットキー・手動取り込み）が常に機能することを保証する。

**多重起動の防止は、Windows・Linux とも名前付き Mutex のみで足りる。** ロックファイル方式（データディレクトリ配下への専用ファイル作成）は採用しない。ただし .NET の名前付き Mutex は、`Global\` プレフィックスを付けない場合は既定で**セッション単位のスコープ**になる（Linux 実装では実体として `/tmp/.dotnet/shm/session<セッションID>/` 配下にファイルが作られる）。デスクトップ環境ではログインシェル・ターミナル・ファイルマネージャからのダブルクリックなど、起動経路によってセッションが分かれることが普通にあり、プレフィックス無しでは同じ発行フォルダの Graft を2つ起動しても双方が起動してしまう（`setsid` で意図的に別セッション化した2プロセス間の実機検証で確認: `Graft.SingleInstance.Mutex` は2つ目もACQUIREDされ多重起動を防げないが、`Global\Graft.SingleInstance.Mutex` なら2つ目はBLOCKされ正しく防げる）。そのため **`Global\` プレフィックスを必ず付与する**。Windows では `Global\` はターミナルサービス（RDP等のマルチセッション環境）のグローバル名前空間を指す既存の構文であり、通常の名前付きMutexとして機能する（この変更による Windows 側の挙動変化はない）。`Global\` 名前空間へのオブジェクト作成が権限で拒否される限られた環境（Session 0 分離下で動くサービスや一部の制限付きアカウント等）では、`Global\` 無しの名前へ縮退し（セッション内のみの検知に後退する）、それも作成できない場合は「判定不能」を「多重起動とみなして起動を止める」ではなく「起動を許可する」側に倒す。多重起動防止はデータ破損を防ぐための安全機構であり、権限問題だけで利用者が単独起動すらできなくなる方の実害が大きいと判断したため。

多重起動の判定は**発行フォルダ単位**で行う。Mutex名は固定文字列ではなく、発行フォルダ（実行ファイルと同じディレクトリ、2.6）の絶対パスから導出した SHA-256 ハッシュを混ぜ込んで組み立てる。6.8 が守ろうとしているのは「バックアップとリビジョン番号の整合が複数プロセスから壊されないこと」であり、対象は `settings.json`・`projects.json`・`back/`・`queue.json`・`logs/` といった発行フォルダ配下のデータに限られる。発行フォルダが異なれば読み書きするデータディレクトリも完全に分かれるため実害が無く、同時起動を妨げる理由が無い（例: 本番用と検証用を別フォルダに置いた2つの Graft、USBメモリのポータブル版と手元のコピーを同時に開く、等）。そのため、**同じ発行フォルダの2つ目の起動だけを多重起動として防ぎ、別の発行フォルダに置いた Graft は互いに独立したインスタンスとして動作する。**

### 2.4 プラットフォームサービスの抽象化

OS固有機能は `Graft.Platform` 名前空間のインターフェースとして定義し、実装を `Platform/Windows/` `Platform/Linux/` に分ける。**UI層・機能層はインターフェースにのみ依存する。**

```
IPlatformServices
├── ITrayIcon              トレイ常駐
├── IGlobalHotkeys         グローバルホットキー
├── IClipboardMonitor      クリップボード監視
├── ITrashService          ごみ箱への削除
├── IFileManagerLauncher   ファイルマネージャで表示
├── ISystemThemeWatcher    システムテーマの判定と変更通知
└── ISingleInstanceGuard   多重起動の防止と既存ウィンドウの前面化
```

各インターフェースは `bool IsSupported { get; }` を持ち、**利用可否をUIが判断できる**ようにする。利用不可の機能に対応する設定項目は、設定画面で無効表示にし理由を併記する。

いずれのプラットフォームでも成立しない場合に備え、**何もしない実装（NullObject）を必ず用意する**。呼び出し側が `null` 判定を書かなくて済むようにする。

### 2.5 フォント

プラットフォームで利用可能なフォントが異なるため、**フォールバックの並びで指定する**（先頭から利用可能なものを使う）。

| 用途 | 指定 |
|---|---|
| UI | Yu Gothic UI, Segoe UI Variable, **Noto Sans CJK JP, IPAexGothic**, sans-serif |
| コード | Cascadia Mono, **JetBrains Mono, Noto Sans Mono CJK JP, DejaVu Sans Mono**, monospace |

日本語グリフを持つフォントが1つも見つからない環境では、**起動時に警告を表示**する（`E705`）。文字化けを無言で放置しない。

### 2.6 フォルダ構成

実行ファイルと同じ階層に配置する（v2.0 と同一。ポータブル運用を優先し、XDG のディレクトリ規約には従わない）。

```
Graft/
├── Graft(.exe)
├── settings.json / projects.json / templates.json / queue.json / layout.json
├── onboarding.done
├── back/<プロジェクトID>/history.jsonl, r24_.../manifest.json …
└── logs/yyyyMMdd.log
```

実行ファイルのあるディレクトリが書き込み不可の場合（Windows で `Program Files` 配下、Linux で `/usr/local/bin` 等に置かれた場合）、起動時に軽量な書き込み確認（一時ファイルの作成・削除のみ）を行う。書き込めない場合は日本語のダイアログでその旨・原因を明示したうえで、起動自体は続行する。設定・履歴・バックアップ・ログのいずれも保存できない状態が続いている間は、ステータスバーに常時警告を表示し続ける。**この書き込み確認自体は、検出したその場で別の場所へ自動的にデータを逃がすものではない**（後述のとおり、この方針は維持している）。

起動時の書き込み確認はログより前に行う。**書き込めない状況ではログにすら記録できない**ため、通知はログを経由せずダイアログのみで行う。詳細は `Infra/AppPaths.CanWriteToBaseDirectory` および `Views/StartupCoordinator.WriteCheck.cs` を参照。

**方針転換の経緯（v1.0.x）**: v2.0・v2.1の当初はここで、「別の場所へ自動的にフォールバックはしない」に加え、「利用者自身にフォルダを書き込める場所へ移動してもらう方がこの製品の性格（実行ファイルの隣にすべてがある）に合っている」として、移動を助ける機能そのものを持たない方針を明記していた。

しかし実際に運用してみると、`Program Files` 配下等の書き込み不可な場所へ置いてしまった利用者に「設定・履歴・バックアップ・ログを漏れなく手作業でコピーし、実行ファイルの隣へ戻す」よう求めるのは負担が大きく、コピー漏れによるデータの実質的な消失（バックアップが無ければ「元に戻す」も機能しない）にもつながりかねない。**製品としての安心感を欠く**と判断し、この移動作業そのものを設定画面から安全に行える機能（**データ保存先の選択**、2.7章）を追加した。

ただし、これは「起動時に書き込み不可を検出した瞬間、黙って別の場所へ切り替える」という自動フォールバックではない。**切り替えは常に利用者が設定画面で明示的に選んで実行する操作であり**、本節冒頭の書き込み確認とダイアログ表示の挙動そのものは変えていない。「自動フォールバックは採用しない」という判断自体は維持したまま、「移動という作業を利用者の手作業に丸投げしない」ための道具を用意した、という位置づけである。

### 2.7 データ保存先の選択（機能追加）

設定画面「一般」タブから、データ保存先を「**ポータブル**（実行ファイルと同じフォルダ。2.6の既定）」と「**ユーザーフォルダ**（`%APPDATA%\Graft` 相当。`AppPaths.DefaultUserDataDirectory()`）」の間で切り替えられる。利用者からは「移動」として見える操作で、ボタンの文言も現在のモードに応じて「ユーザーフォルダへ移動」／「ポータブルへ戻す」と変わる。

**保存先の決め方（循環の回避）**: settings.json 自体に保存先を書くと、「settings.json の場所が settings.json の中身に依存する」循環に陥る（保存先を読むにはまず settings.json を読む必要があるが、settings.json の場所自体が読めていない）。これを避けるため、settings.json より手前・かつ場所が固定（実行ファイルと同じ階層）の、1行だけのポインタファイル `datapath.txt`（`Infra.DataDirectoryPointer`）にデータ保存先の絶対パスを書く。`AppPaths.ResolveBaseDirectory` はこのポインタファイルだけを読んで基準ディレクトリを決める。ポインタファイルが無い・空・読み取れない場合は、従来どおり実行ファイルと同じ階層（ポータブル、2.6の既定）を使う。

**切り替えの手順（`Infra.DataDirectoryMigrator`）**: 「コピー→検証→ポインタ切り替え」の順で行い、失敗した場合は元データに一切手を加えない。

1. **コピー**: 対象ファイル（settings.json・projects.json・templates.json・queue.json・onboarding.done・layout.json）と対象ディレクトリ（back/・logs/）を新しい場所へコピーする。コピー先へは書くが、**コピー元へは一切書き込まない**。ディスク不足等でコピーが途中失敗しても、元の場所のデータは常に無傷のまま残る
2. **検証**: コピー元に存在するファイル・ディレクトリが、コピー先にも存在することを確認する
3. **ポインタ切り替え**: 1・2が両方成功した場合のみ `datapath.txt` を書き換える（ユーザーフォルダへ移行する場合は新しい場所を書き、ポータブルへ戻す場合はポインタファイル自体を削除する）。コピー・検証のいずれかに失敗した場合はポインタに一切触れない（`ErrorCode.E407`）ため、次回起動時も従来の場所が使われ続ける

**削除は次回起動時に行う**: 実行中のプロセスは、コピー後も引き続き元の場所を指す `AppPaths` インスタンス（起動時に一度だけ生成し、SettingsStore・ProjectStore・Logger 等へ配り済み）を使って動作し続けている。実行中に参照先を差し替える大掛かりな変更は行わないため、移行のその場では元データを削除しない。移行成功後は、新しい保存先へ「後始末待ち」マーカー（`pending-cleanup.txt`）を書くだけに留め、実際の削除は次回起動時に `DataDirectoryMigrator.RunPendingCleanup` が「元の場所→新しい場所へもう一度取り込み直してから削除する」ことで安全に行う（再起動を後回しにした間に行った設定変更等も、この再取り込みで拾える）。移行完了の通知ダイアログには「再起動」ボタンがあり、押すと実際に再起動する（実行ファイルの場所を特定できない等で自動再起動できない場合は手動再起動を案内する）。

**孤立したユーザーフォルダの復帰確認**: Graft はインストーラを持たない配布のため、(1)新しい版へ更新するため実行ファイルのフォルダの中身を丸ごと差し替える、(2)新しくダウンロードして別の場所に展開する、のいずれでもポインタファイル（実行ファイルの隣にしか置けない）が失われる。この状態で以前ユーザーフォルダへ移行していた場合、過去のデータ（設定・登録済みプロジェクト一覧・適用履歴とバックアップ）が実在するのに一切使われないまま、初回起動ガイドが再表示されてしまう。これを防ぐため、起動のごく初期に次の3条件がすべて成り立つときだけ「以前ユーザーフォルダに保存したデータが見つかりました。こちらを使いますか？」と確認する（`Infra.DataDirectoryRecovery.ShouldPromptForRecovery`）。

1. 実行ファイルと同じ階層に `datapath.txt` が無い（保存先が未確定）
2. 実行ファイルのフォルダ自体に Graft の既知のデータが1つも無い（**最も重要な安全弁**。USB 等で実行ファイルのフォルダを別の PC へ持ち運んだ先にたまたま `%APPDATA%\Graft` が残っていても、持ち運んだ側に既にデータがあるためこの条件で不成立となり、他人〔そのPCの以前の利用者〕のデータへ乗っ取られることはない）
3. 既定のユーザーフォルダに既知のデータが1つ以上ある

「はい」で復帰（ポインタをユーザーフォルダへ書く）、「いいえ」で以後尋ねないポータブル明示（ポインタに実行ファイル自身の場所を書く）とする。「キャンセル」（タイトルバーの×を含む）を選んだ場合は、その場で Graft 自体を終了する。起動をそのまま続けると、続く起動処理（back/・logs/ の作成、settings.json の書き込み等）によって実行ファイルのフォルダ自体に既知の Graft データができてしまい、次回起動時には条件2が永久に不成立となって、以後この確認自体が二度と出せなくなるためである。

**エラーコード**: 保存先の移行（コピー・検証）に失敗した場合は `E407`（17章）。

### 5.1 unified diff 入力対応（v2.1で追加）

形式指示の無い会話で、AIが Graft 独自形式ではなく **unified diff**（```diff フェンス、`--- a/X` / `+++ b/X` ヘッダ、`@@ ... @@` ハンク）で出力することが多いため、これを直接受け付ける。

**受け付ける形式**

- `--- a/X` と `+++ b/X` のヘッダ対に続く1つ以上の `@@ ... @@` ハンク。`a/` `b/` 前置・タブ区切りのタイムスタンプは無視する。
- ```diff 等のMarkdownコードフェンスは剥がしてから解析する。
- 新規ファイル（`--- /dev/null`）・削除ファイル（`+++ /dev/null`）。
- `\ No newline at end of file` 注記は無視する（クラッシュしないことのみ保証する）。

**変換の考え方（`UnifiedDiffAdapter`）**

unified diff を**既存の SEARCH/REPLACE ペア・FULL形式ブロックへ変換するアダプタ**として実装し、マッチング（6章）・プレビュー・適用（7章）・リビジョン（8章）の既存パイプラインをそのまま再利用する。

| unified diff | 変換先 |
|---|---|
| 通常のハンク（1ハンク＝1変換単位） | SEARCH = 文脈行(` `)＋削除行(`-`)、REPLACE = 文脈行＋追加行(`+`)。行頭の1文字は剥がす |
| 新規ファイル（`--- /dev/null`） | FULL形式のブロック相当（全ハンクの文脈行＋追加行を連結した内容） |
| 削除ファイル（`+++ /dev/null`） | DELETEブロック（4.6） |

ハンク見出し（`@@ -n,m +n,m @@`）の行番号は**一切参照しない**。マッチングエンジン（6章）は行単位の完全一致→トリム一致→類似度一致の段階的フォールバックを持つため、AIが返す diff の行番号がファイルの実際の位置とずれていても、文脈行の内容さえ合っていれば位置決めできる。

パッチメタデータ（4.2）に相当する情報が無いため、summary は固定文言「unified diff からの取り込み」、type は `chore` を補う。これにより `requireSummary` 設定（15章）の必須チェックには引っかからない。

**接続点**: `PatchParser.Parse` は、入力に Graft形式のブロックヘッダ（`<<<<...`）が1つも無く、かつ unified diff として解釈できる場合にのみアダプタへ委譲する。Graft形式のマーカーが1つでもあれば、従来どおり4章の解析を優先する。クリップボード監視の「パッチらしさ」判定（10章）も同じ特徴で unified diff を検知する。

**制限**

- ハンクに文脈行・削除行が1つも無い（純粋な追加のみの）ハンクは、SEARCH部が空になり位置決めできないため、警告付きで取り込みから除外する。
- git拡張ヘッダ（`diff --git` の rename/copy 情報等）は解釈しない。ファイルパスは各セクションのヘッダ行（`--- ` / `+++ `）からのみ判定する。
- 複数ファイルにまたがる巨大な diff でも、ファイルセクション単位で独立して変換するため、1ファイルの変換に失敗しても他ファイルの取り込みは継続する。

### 5.2 標準SEARCH/REPLACE形式 入力対応（v1.0.14で追加）

5.1 と同じ理由（形式指示の無い会話でAIが Graft 独自形式に従わない）から、より一般的な **SEARCH/REPLACE ブロック形式**（以下「標準SR形式」）を直接受け付ける。Aider が広め、Cline・Roo Code 等も採用した事実上の標準で、マーカーが git のマージコンフリクトマーカーそのものであるため、LLMが学習済みで自然に出力できる。**v1.0.14 で既定のプロンプトテンプレートもこの形式へ切り替えた**（4.8）。

**「標準」の裏取り（2026-08 時点）**

Aider公式ドキュメント（`aider.chat/docs/more/edit-formats.html`）と Aider 本体のプロンプト実装（`aider/coders/editblock_prompts.py`）を実際に参照して、以下を確認した。

- ファイルパスは「フェンス付きコードブロックの**直前に、パスだけを単独の行として**」置く（原文: *"The \*FULL\* file path alone on a line, verbatim. No bold asterisks, no quotes around it, no escaping of characters, etc."*）。
- 新規ファイルの作成は「**SEARCH部を空にする**」で表す（原文: *"a new file path, including dir name if needed, an empty `SEARCH` section, the new file's contents in the `REPLACE` section"*）。
- **素の標準SR形式に `NEW_FILE` / `WHOLE_FILE` / `DELETE_FILE` というマーカーは存在しない。** これらは利用者の会社で運用されている「SRルール」による独自拡張である。
- ファイルの削除・改名は素の標準SR形式の守備範囲外（Aider は応答末尾のシェルコマンドで表す）。

**受け付ける形式**

Graftは、素の標準（空SEARCH方式）と会社ルール（マーカー方式）の**両方**を受け付ける。どちらで届いても内部表現は同じになる。

| 標準SR形式の書き方 | 変換先 |
|---|---|
| パス行 ＋ `<<<<<<< SEARCH` 〜 `=======` 〜 `>>>>>>> REPLACE` | SEARCH/REPLACE ペア（4.3） |
| 同上で **SEARCH部が空**（素の標準の新規ファイル作法） | FULL形式ブロック（4.5）相当 |
| パス行 ＋ `<<<<<<< NEW_FILE` 〜 `>>>>>>> END_FILE` | FULL形式ブロック（4.5）相当 |
| パス行 ＋ `<<<<<<< WHOLE_FILE` 〜 `>>>>>>> END_FILE` | FULL形式ブロック（4.5） |
| パス行 ＋ `<<<<<<< DELETE_FILE` 〜 `>>>>>>> END_FILE` | DELETEブロック（4.6） |

`NEW_FILE` と `WHOLE_FILE` を区別せず同じ内部表現にするのは、Graft の FULL形式が「存在しなければ作る／存在すれば全面的に置き換える」という一つの動作であり、AI側の意図で適用結果が変わらないため。

**変換の考え方（`StandardSearchReplaceAdapter`）**

5.1 と同じく**アダプタ**として実装し、マッチング（6章）・プレビュー・適用（7章）・リビジョン（8章）の既存パイプラインをそのまま再利用する。4章の解析（`PatchParser`）には手を入れないため、履歴・パッチキューに残っている既存データの解釈は一切変わらない。

パッチメタデータ（4.2）に相当する情報が無いため、summary は固定文言「標準SEARCH/REPLACE形式からの取り込み」、type は `chore` を補う（5.1 と同じ前例）。これにより `requireSummary` 設定（15章）の必須チェックには引っかからない。

**接続点（5.1 との判別）**

`PatchParser.Parse` は次の順で振り分ける。

1. 入力が `NEED_MORE_CONTEXT` の1行だけ → `E710`（後述）。
2. Graft形式のマーカーが1つも無く、unified diff として解釈できる → 5.1 のアダプタ（**判定条件は 5.1 のまま変更しない**）。
3. **Graft 独自形式にしか存在しないヘッダ**（`<<<< FILE:` / `<<<< PATCH` / `<<<< DELETE:` / `<<<< RENAME:` / `<<<< MKDIR:` / `<<<< APPEND:` / `<<<< PREPEND:`）が1つも無く、標準SR形式の開始マーカーがある → 5.2 のアダプタ。
4. それ以外 → 従来どおり4章の解析。

**この判別の要は `<<<<<<< SEARCH` が両形式で完全に共通であること。** これを手がかりに形式を決めてはならない（決めると既存の Graft形式パッチがすべて壊れる）。両形式を区別できる唯一の手がかりは**直前のファイル指定行**であり、Graft形式は `<<<< FILE: パス`、標準SR形式はパスだけの裸の行である。そのため手順3では `<<<<<<< SEARCH` を除いた「Graft専用ヘッダ」の有無で振り分ける。

**両形式が混在した場合: Graft形式を優先する。** 5.1 の接続点の規則に揃えるため、および混在時に標準SR形式を優先すると既存の `<<<< FILE:` ブロックが解釈されなくなり後方互換が壊れるため。混在した入力は Graft形式として解析され、標準SR形式側のマーカーは未知のヘッダとして `E002` になる（黙って一方を取りこぼすより失敗させて気づかせる）。既定テンプレートでも「1回の出力で2つの形式を混ぜない」ようAIへ明示的に指示する。

**パス指定行の判定**

裸の1行をパスとして扱うため、AIの説明文（地の文）を誤ってパスと解釈する危険が Graft形式より格段に高い。次の3条件をすべて満たす行だけをパス指定行とみなす。

1. 空白を1文字も含まない（英文の地の文を弾く）。
2. `.` または `/` を含む（日本語の地の文を弾く。全角の `。` は `.` ではない）。
3. パスに使える文字（英数字・各国語の文字・`. / \ _ - + ~ @ # :`）だけで構成される。**拒否リストではなく許可リスト**とする。日本語の文は空白を含まないため条件1では弾けず、`【原則】既存ファイルの修正はSEARCH/REPLACE形式を使い、` のような行が `/` を含むためにパスと誤認される事故が実際に起きた。全角の約物は無数にあり拒否リストでは漏れる。

`**パス**`・`` `パス` ``・`"パス"`・末尾の `:` といった装飾は取り除いてから判定する（Aider は装飾を禁じているが、実際のAIは付けてくるため）。取り除いた後のパスは、Graft形式と**同一の検査**（`PatchTextUtil.TryNormalizePath`。絶対パス・`..` を拒否）を必ず通す。

2つ目以降のブロックでパス行が省略された場合は、直前のブロックと同じファイルへの続きとみなす。

**`NEED_MORE_CONTEXT`（`E710`）**

会社ルールの運用規定では、AIは SEARCH 部を正確に作れない場合に `NEED_MORE_CONTEXT` の1行だけを返す。これを `E001`（ブロックが存在しない）として扱うと「AIが変な出力をした」としか見えず、実際の状況（AIが情報不足を訴えており、対象ファイルを渡し直せば解決する）が伝わらないため、専用の `E710` で区別する（17章）。クリップボード監視（10章）でもこの1行を検知対象に含め、「コピーしたのに何も起きない」状態にしない。

**制限**

- コードフェンス行（```` ``` ````）を読み飛ばすのは**ブロックの外側だけ**とする。標準SR形式の本文は「ファイルの中身そのもの」であり、Markdownファイルの編集では本文が正当に ```` ``` ```` を含むため（5.1 の一律除去とは異なる）。
- 拡張子も区切りも持たない実在のファイル名（`Dockerfile`・`Makefile` 等）だけを対象とするパッチは、パス指定行として認識できない（地の文と原理的に区別が付かないため。10章のパスの実在らしさ判定と同じトレードオフ）。この場合は Graft形式（`<<<< FILE: Dockerfile`）で出力すれば従来どおり扱える。
- ファイルの改名（`RENAME`）・フォルダ作成（`MKDIR`）・追記（`APPEND` / `PREPEND`）は標準SR形式では表せない。Graft 独自形式へ切り替えて出力する。
- Graft 独自の追加記法のうち `OCCURRENCE=`・`SEARCH-RANGE`・`# 説明` は、標準SR形式のブロックでもそのまま使える（4章の SEARCH マーカーと同じ書き方）。

```json

    "trayEnabled": true,
    "globalHotkeyEnabled": true,
    "clipboardWatchEnabled": false,
    "useTrashOnDelete": true
  },
  "update": {
    "checkOnStartup": true,
```

これらは**利用可能な場合のみ有効**になる。利用不可の環境では設定値にかかわらず無効として扱い、設定画面にその理由を表示する（例: 「この環境（Wayland）ではグローバルホットキーを登録できません」）。`git.autoCommit`（既定`false`）は4.7章の自動コミット機能のオン・オフ。

### 15.1 自動更新（機能追加）

配布方式はメインリポジトリ（`Yu5rin/Graft`）を公開し、GitHub Releases を更新の配布先として使う。トークンや専用の配信サーバは不要。

- **確認**: `GET <checkUrl>`（既定は上記の GitHub Releases API。`Accept: application/vnd.github+json`・`User-Agent: Graft/<バージョン>` を付与）を呼び、`tag_name`（`v1.0.7` 形式）を現在のバージョンと**数値として**比較する（文字列比較では `1.0.10` < `1.0.9` と誤判定するため）。`releases/latest` はプレリリースを返さない仕様のため、プレリリース（例: v1.0.6）は自動更新の対象にならない。
  - 起動時: `checkOnStartup` がオンなら、**起動のたびに必ず確認する**（v1.0.12。以前は前回の確認日時 `update-check.json` から24時間以上経過していることを条件にしていたが、設定画面のチェックボックスの文言「起動時に更新を確認する」と実態が食い違っていたため、この絞り込みを廃止した。`update-check.json` の前回確認日時自体は「バージョン情報」タブの「最終確認」表示のためだけに残る）。ただし、テーマ変更・データ保存先の移動・自動更新の適用後などGraft自身が自己再起動して起動した場合（起動引数 `--graft-restarted`。`Infra.AppRestart` 参照）は、`checkOnStartup` がオンでも確認しない。「起動のたびに確認する」の対象は利用者が自分の意思で起動したときに限られ、Graft自身の都合による再起動まで対象にする理由が無いため。`checkOnStartup` がオフなら、いずれの場合も通信しない。
  - 手動: 設定画面「更新」の『今すぐ更新を確認』は上記のいずれの条件も無視して必ず確認する。
  - 通信は非同期で行い、起動（18章「1秒以内」要件）を一切ブロックしない。通信の失敗は握りつぶし「確認できなかった」として扱う。
- **ダウンロードと検証**: 新しいバージョンが見つかった場合のみ、利用者の同意を得てから配布物（win-x64 の ZIP）をダウンロードする。HTTPS 必須。GitHub のリリースアセットが持つ `digest`（`sha256:...`）と実際に計算した SHA256 を突き合わせ、一致した場合のみ次へ進む。`digest` が無い・解釈できない場合は検証不能としてインストールを中止する。ZIP の中身は配布物の6ファイル（`Graft.exe`・ネイティブDLL3つ・`取扱説明書.md`・`はじめにお読みください.txt`）とだけ一致することを展開前に確認し、想定外のファイルが1つでもあれば中止する（settings.json・projects.json・back/・logs/ 等の利用者データを絶対に巻き込まないため）。ダウンロード・展開に使う一時作業フォルダ（`%TEMP%\GraftUpdate\<GUID>\`）は、処理完了後（成功・失敗いずれも）そのプロセスがフォルダごと掃除する。
- **自己置き換え**: 実行中のファイルは上書きできないがリネームはできる性質を使い、対象ファイルを `<ファイル名>.old` へ退避してから新しいファイルを配置する。書き込み権限が無い場所（`Program Files` 等）では自動更新をあきらめ、リリースページからの手動更新を案内する。途中で失敗した場合は退避した分だけ正確に元へ戻す。未保存の編集がある場合は再起動前に保存を促す。退避ファイル（`.old`）は次回起動時に掃除する。
- **一時作業フォルダのクラッシュ対策（v1.0.12）**: ダウンロード中に強制終了・クラッシュした場合、そのプロセス自身では作業フォルダを掃除できない（50MB超のZIPが残りうる）。次回起動時に `%TEMP%\GraftUpdate\` 直下を走査し、作成から24時間以上経過した子フォルダだけを削除する（実行中の更新を誤って消さないための閾値）。`%TEMP%\GraftUpdate\` の外は一切対象にしない。
- 設定画面「一般」タブに、起動時に確認するかどうかの切替・チェック先URL（変更可能）・『今すぐ更新を確認』を置く（14章と同じ即時反映方式）。

## 16. ログ

v2.0 を維持する。**起動時にプラットフォーム情報を1行記録する**（`IPlatformServices.DescribeEnvironment()`）。不具合の切り分けに必要なため。ファイルの中身そのものは引き続き記録しない。

記録する内容は OS 種別・バージョンと、利用可能なプラットフォームサービス（トレイ・ホットキー・クリップボード監視等）の対応可否。Linux ではこれに加えて、環境変数 `XDG_SESSION_TYPE` の値（`x11` / `wayland`）を「セッション」として記録する。**これは GNOME・KDE 等の「デスクトップ環境」そのものではなく、X11/Wayland のどちらのディスプレイサーバ方式で動作しているかを示すセッション種別である**点に注意（デスクトップ環境の判別自体は行っていない）。

### 16.1 ログの参照手段（機能追加）

設定画面「バージョン情報」タブから、ログを直接参照できる。

- **「ログフォルダを開く」**: `logs/` フォルダを OS のファイルマネージャで開く（`IFileManagerLauncher`）。フォルダが無ければ先に作成してから開く
- **「最新のログを表示」**: 最新の `yyyyMMdd.log` の末尾（既定200行）を専用ウィンドウに表示する（`LogTailReader`）。ログファイルが1つも無い場合はその旨を案内する。表示内容は全文コピーできる

いずれもログの実体（ファイル）には一切書き込まず、既存のログファイルを読むだけの補助機能。

### 17.1 エラー詳細のコピー（機能追加）

エラーコードを含むダイアログ（`Platform.AvaloniaDialogService` の確認・通知系メソッド共通）には、「詳細をコピー」ボタンを左詰めで表示する。メッセージ中にエラーコードのパターン（`E` + 数字3桁）が含まれる場合にのみ表示され、通常の確認メッセージ（エラーコードを含まないもの）では表示されない。

## 18. 非機能要件

v2.0 の要件を維持し、以下を追加・変更する。

- 起動から操作可能まで1秒以内（**両プラットフォームで**）。初回起動・2回目以降を問わず満たす
  （配布形式の変遷は2.1・20.1・附録B参照。ネイティブライブラリを自己展開する単一ファイル形式
  〔`IncludeNativeLibrariesForSelfExtract=true`〕では初回起動時のみこの要件から外れていたが、
  自己展開をしない現行の単一ファイル形式〔false〕では発生しない）
- 10万行のファイルを開いてスクロール・編集が遅延なく行えること（**両プラットフォームで**）
- ファイル横断検索は10万ファイル規模でもUIをブロックしない
- 常駐時のメモリ使用量150MB以下。**プロセスの「プライベート専有メモリ」で判定する**
  （Windowsのタスクマネージャの「メモリ」列、Linuxでは `/proc/<pid>/smaps_rollup` の
  `Private_Dirty` に相当）。`ps` の RSS や Linux の `VmRSS` は実行ファイル・共有ライブラリの
  ファイルマップ分を含むため、この基準よりかなり大きい値が出る。ファイルマップはメモリ
  不足時にOSが破棄・再読込できる領域であり、単純な合計RSSは常駐負荷の実態と乖離するため、
  誤解を避けるために測定方法をここで明記する（実測は20.1参照）
- ネットワーク通信は自動更新の確認・ダウンロードのときだけ（15.1章）。それ以外の外部通信（使用状況の送信・テーマのダウンロード等）は搭載しない
- **（新規）UIの自動検証**: 主要画面の描画・主要操作シナリオが headless テストとして自動実行でき、**CI相当の環境（画面なし）で完結すること**。リソース解決の失敗とレイアウト崩れをテストで検出できること

| 10万行のファイル | 読み込みと初回描画 342ms / スクロール 135ms / 編集 77ms / レキサ走査 339ms |
| 常駐時のメモリ使用量 | Linux実測（フォルダ形式時点）: 18章の基準である**プライベート専有メモリで約75MB**、150MB以下の目標を満たす。参考として`ps`/`VmRSS`基準のRSSは約196MBで、ファイルマップ分を含むため大きく出る（内訳は本節末尾参照）。現行の単一ファイル形式（自己展開なし）では、実行ファイル自体のファイルマップ先が変わるのみで確保する匿名メモリ量に変化はないと考えられるが、再測定はしていない |

**配布形式の変更1（L5完了後、単一ファイル→フォルダ形式）**: L5完了時点では単一実行ファイル
（PublishSingleFile）で発行していたが、これは起動のたびに自分自身を一時ディレクトリへ
展開してから実行する方式で、初回起動が約5.44秒に達し18章の起動要件（1秒以内）から
外れていた（展開結果は再利用されるため2回目以降は約0.84秒）。**フォルダ形式へ変更**した
結果、初回・2回目以降を問わず約0.85秒で安定し、要件を満たすようになった。発行サイズも
約116MBから約105MBへ縮小した。ReadyToRunは無効化を試したところRSSがむしろ増え起動も
遅くなったため（Graft.csprojのコメント参照）、引き続き有効のまま維持する。

**配布形式の変更2（フォルダ形式→単一ファイル形式・自己展開なし）**: フォルダ形式は要件は
満たしたものの、発行物が**216ファイル・約109MB**に散らばり「発行フォルダの中が
ごちゃごちゃしている」という利用上の不満につながった。依存DLLを`lib/`等の子フォルダへ
まとめる案を検証したが、ホストが`Graft.deps.json`のNuGetパッケージ構造どおりの相対パス
（`lib/net8.0/Avalonia.Base.dll`）でDLLを探すため、フラットな配置はもちろん単純な
子フォルダへの移動でも `FileNotFoundException: Could not load file or assembly
'Avalonia.Base'` となり起動不能だった。`runtimeconfig.json`への`additionalProbingPaths`
追加でも解決しなかった。

変更1で問題だったのは単一ファイル形式そのものではなく、**`IncludeNativeLibrariesForSelfExtract=true`**
（ネイティブDLLを実行時に一時フォルダへ自己展開する設定）だったと判明した。そこで
`PublishSingleFile=true`は維持しつつ`IncludeNativeLibrariesForSelfExtract`を明示的に
**false**にして単一ファイル形式へ戻した。falseであれば実行時展開が発生せず、管理コードも
バンドルから直接読まれるため遅くなる理由がない。実測（Linux、同一条件）でも
フォルダ形式 798〜1145ms に対し単一ファイル形式（自己展開なし） 622〜637ms と、
むしろ高速だった。発行物は**216ファイル→4ファイル**（実行ファイル＋ネイティブDLL3つ）
に減り、サイズは約121MBとなった（フォルダ形式より増えるが、ファイル数の削減を優先する）。
`EnableCompressionInSingleFile`も圧縮すると展開が必要になり起動が遅くなるため、
falseのまま維持する。設定はGraft.csprojに既定値として記述してあり、`dotnet publish`時に
`-p:`指定を追加しなくてもこの形式になる。

`/proc/<pid>/smaps_rollup` によるメモリ内訳（フォルダ形式時点、Linux実測、起動直後）:

| 項目 | 値 | 内容 |
|---|---|---|
| Rss | 約201MB | プロセス全体のRSS（`ps`/`VmRSS`が示す値に相当） |
| Pss_Anon | 約56MB | アプリが実際に確保した匿名メモリ |
| Pss_File | 約114MB | 実行ファイル・ライブラリのファイルマップ（メモリ不足時にOSが破棄・再読込できる） |
| Pss_Shmem | 約19MB | X11の共有メモリ（グラフィックスバッファ） |
| Private_Dirty | 約75MB | 解放できない専有メモリ（18章のメモリ目標の判定基準） |

RSSの大半はディスク上のファイルをマップしたページが占めており、常駐負荷の実態を表す
指標としては`Private_Dirty`（プライベート専有メモリ）の方が適切なため、18章の目標値は
これを基準とすると定義した。GCのチューニング（`System.GC.Concurrent=false`・
`Server=false`・`RetainVM=false`・`Conserve=5`）も試したが、RSSは約196.6MBのまま
変化がなく効果が確認できなかったため採用しない。

### 20.2 実機確認で見つかった不具合（リリース前の通し確認）

画面のある環境（Xvfb）でアプリを起動し、5巡にわたって各機能を操作して確認した。
静的な検査やheadlessテストでは現れず、実際に触って初めて分かった不具合は以下のとおり。
いずれも修正し、回帰テストを添えている。

| 症状 | 原因 |
|---|---|
| 保存するたびカーソルが文末へ飛ぶ | 自分の保存をファイル監視が外部変更と見なし、文書を丸ごと差し替えていた |
| 保存したテーマが再起動で元に戻る | 起動時に設定を読み直してテーマを当て直していなかった |
| 複数行の入力欄で内容が途中で切れる | 共通テーマがスクロールバーの指定を無視し、中央寄せのまま固定していた |
| 透かし文字がまったく表示されない | 共通テーマのテンプレートが透かし文字を描画していなかった |
| 「解析」を押しても何も起きない場合がある | クリップボードを読めないとき、理由を示さず黙って処理を終えていた |
| ライトテーマでトグルボタンだけ浮いて見える | ToggleButtonにテーマ定義が無く、Avaloniaの既定色が当たっていた |
| 起動ログに未処理例外が記録される | 破損ファイルの退避が同時に走ると、移動済みのファイルを再度移動しようとしていた |
| OS固有機能 | Windows・Linux とも全機能が有効。利用できない項目は起動ログと起動時通知で提示する |

**Wayland での制約**: グローバルホットキーは他クライアントのキーをつかみ取れないため利用できない。
起動時に E601 として通知し、他の機能はそのまま使える。

30. **性能テストの穴を塞いだ**（18章）。従来の10万行の性能テストはすべて折り返しオフのエディタで計測しており、Graftの既定（`editor.wordWrap` は既定オン）で利用者が実際に通る折り返し経路の性能が一度も検証されていなかった。折り返しを有効にした状態での「読み込みと初回描画」「スクロール」の計測を追加し、あわせて計測対象が本当に折り返しているかを確かめる前提チェックも入れた
31. **標準SEARCH/REPLACE形式の入力対応を追加し、既定のプロンプトテンプレートをこの形式へ切り替えた**（5.2・4.8・10章・17章）。項目15（unified diff）と同じ「AIが独自形式に従わない」という事情に対し、より一般的な標準SR形式（Aider が広め Cline・Roo Code 等も採用。マーカーが git のマージコンフリクトマーカーそのものであるためLLMが自然に出せる）へ寄せた。`StandardSearchReplaceAdapter` が SEARCH/REPLACE ペア・FULL形式ブロック・DELETEブロックへ変換し、既存パイプラインを再利用する。実装にあたって Aider の公式ドキュメントと本体のプロンプト実装を実際に参照し、**素の標準SR形式では新規ファイル作成を「SEARCH部を空にする」で表し、`NEW_FILE` / `WHOLE_FILE` / `DELETE_FILE` というマーカーは存在しない**（これらは利用者の会社の運用ルールによる独自拡張である）ことを確認したうえで、**両方の書き方を受け付ける**設計とした。`<<<<<<< SEARCH` の行が両形式で完全に共通であるため、形式の判別は `<<<< FILE:` 等のGraft専用ヘッダの有無で行う。混在時は後方互換を優先して Graft形式を優先する。既定テンプレートは標準SR形式へ切り替えたうえで、従来のGraft独自形式のテンプレートも `builtin-graft-*` として一覧から選べる形で残した。AIが情報不足を訴える `NEED_MORE_CONTEXT` の1行に対して `E710` を新設（`E707` は項目19のとおり欠番のため使わない）
