# 変更履歴

## 1.0.13

### 追加
- **AIの回答を「標準SEARCH/REPLACE形式」でも受け付けるようにし、AIへの指示文（プロンプトテンプレート）の既定もこの形式へ切り替えた。** 多くのAIコーディングツール（Aider、Cline、Roo Code など）で使われている一般的な形式で、目印がGitの衝突マーカーそのものであるため、AIが学習済みで自然に出力できる。従来からの課題である「形式を指示してもAIが独自形式に従ってくれない」を、Graft側が形式に合わせにいくことで根本から減らす狙い
  - 受け付ける書き方は4種類。**部分修正**（パスだけの行 → `<<<<<<< SEARCH` / `=======` / `>>>>>>> REPLACE`）、**新規ファイルの作成**（`<<<<<<< NEW_FILE` 〜 `>>>>>>> END_FILE`）、**全面書き換え**（`<<<<<<< WHOLE_FILE` 〜 `>>>>>>> END_FILE`）、**ファイルの削除**（`<<<<<<< DELETE_FILE` 〜 `>>>>>>> END_FILE`）
  - 【調べた結果】実装にあたり、この形式を広めたAiderの公式ドキュメントと本体のプロンプト実装を実際に参照して裏を取った。**素の標準形式では、新規ファイルの作成は「SEARCH部を空にする」で表すのが本来の作法**であり、`NEW_FILE` / `WHOLE_FILE` / `DELETE_FILE` というマーカーは標準には存在しない（これらは運用ルール側の独自拡張）。ファイルの削除・改名も素の標準の守備範囲外だった。そこでGraftは、**空SEARCHによる新規作成と、`NEW_FILE` 等のマーカーによる書き方の両方**を受け付ける。どちらで届いても同じ結果になるので、AIがどちらの流儀で返してきても取り込める
  - パスは必ずプロジェクトからの相対パスとして扱い、`../` で上の階層へ出るパスや絶対パス（`/etc/...`・`C:/...`）は従来のGraft独自形式とまったく同じ検査で拒否する。プロジェクト外への書き込みが起きないことを、テストでも固定した
  - AIが「直す場所を正確に指定できない」と判断したときに返す `NEED_MORE_CONTEXT` の1行を、専用のエラーコード（E710）として区別するようにした。従来の扱い（E001「ブロックが存在しない」）のままでは「AIが変な出力をした」としか見えず、実際には「対象ファイルをもう一度渡せば解決する」という別の状況であることが伝わらないため。クリップボード監視でもこの1行を検知するので、コピーしたのに何も起きない、という状態にならない
  - **従来のGraft独自形式・unified diff形式は今までどおり読み取れる。** 形式の判別は、両形式で共通の `<<<<<<< SEARCH` ではなく「Graft独自形式にしかないヘッダ（`<<<< FILE:` など）があるかどうか」で行うため、履歴やパッチキューに残っている既存のパッチの読み取り方は一切変わらない。既存の自動テストが1件も落ちていないことを確認済み。なお1回の回答に両方の形式が混ざっている場合は、後方互換を優先してGraft独自形式として解析する（この場合、標準形式で書かれたブロックは取り込めず解析に失敗する）ため、AIへの指示文でも「1回の出力で2つの形式を混ぜないこと」を明示している
- プロンプトテンプレートに、従来のGraft独自形式版（「初回用（Graft独自形式）」「継続用（Graft独自形式）」「修正依頼（Graft独自形式）」「新規実装（Graft独自形式）」）を追加した。既定は標準SEARCH/REPLACE形式に切り替わるが、**従来の指示文もそのまま一覧から選べる**。ファイルの移動・改名、フォルダの作成、末尾や先頭への追記、変更全体の要約（summary）はGraft独自形式にしかできないため、必要な場面では引き続きこちらを使える
- 起動時、日本語（ひらがな・カタカナ・漢字）を1文字も描画できるフォントが環境に見つからない場合、その旨をログと起動時の確認ダイアログで警告するようにした（E705）。判定は「Noto Sans CJK JP」等の特定のフォント名との一致ではなく、実際に「その文字を描画できるフォントがシステムにあるか」をOSのフォントサブシステムへ横断的に問い合わせる方式のため、フォールバック列（取扱説明書のフォント設定を参照）に挙げた名前と実際にインストールされているフォントの正式名がわずかに違うだけの環境（例: 「IPAGothic」を「IPAexGothic」と取り違える等）で誤って警告することが無い
- タスクトレイ常駐・自動起動がこの環境では利用できない場合に、その事実をE706としてログへ記録するようにした。設定画面側の案内（該当項目の無効表示）はこれまでどおりで見た目の変化は無いが、実際にどの機能がどの理由で無効になったのかを起動時のログから追えるようになった
- OSのハイコントラストモードを検出できるようにした（E709）。Windowsは`SPI_GETHIGHCONTRAST`、Linuxは対応するデスクトップ設定（GNOMEの`high-contrast`設定）があればそれに追従し、無い場合は何もしない。Graftはプラットフォームや検出結果によらず自前の配色トークンを維持する方針（取扱説明書のテーマ設定を参照）のため配色は切り替えないが、検出できたことは診断用にログへ記録する

### 改善
- **10万行級のファイルでスクロールバーのつまみをドラッグしたとき、表示がマウスに追い付かない問題を大きく改善した（課題#73）。** 10万行のファイルではつまみ1pxが文書の2,244px（約128行）に相当し、1px動かすたびに画面上の46行がすべて作り直される。この1回分のレイアウト費用が、素のエディタ基盤（AvaloniaEdit）の8.3msに対しGraftでは17.0ms（2.12倍）かかっており、ドラッグ中に描画が追い付かなくなっていた。今回これを**10.8ms（1.28倍）**まで下げた。画面の描画まで含めたフレーム全体でも、基準比の上乗せが+13.4ms→**+2.7ms**になっている（実測はいずれも修正前後を同一手順・同一環境で交互25組計測した中央値）
  - 【真因】 上乗せ8.7msのうち**5.1msが折りたたみ**（残りは主に構文強調）だった。エディタ基盤の折りたたみ機能は、画面へ1行描くたびに「この位置より後ろで最初に畳まれている範囲はどこか」を先頭から順に探す作りになっており、**どこも畳んでいないときは範囲の一覧を最後まで舐めきる**（＝一番普通の状態が最悪ケース）。10万行のC#ファイルでは折りたたみ範囲が20,000個できるため、これを46行分繰り返していた。文書のどこをドラッグしているかで費用が変わる（文書の2%地点で+10.8ms、25%で+8.5ms、50%で+5.3ms、75%で+1.3ms＝残りの範囲数に比例する）ことも実測で裏付けた。素のエディタ基盤はどの位置でも一定である
  - 【対処】 **1つも畳まれていない間は、折りたたみの描画部品をエディタ基盤の描画パイプラインから外しておき、1つでも畳まれたら戻す**ようにした。どこも畳んでいないとき、この部品は「何も描かない」ことが確定しているため、外しても表示は完全に同一になる（2,000行のファイルを500行目まで送った状態で描画結果のPNGを比較し、1バイトも違わないことを確認済み。自動テストとしても固定した）。結果、折りたたみによる上乗せは**+5.06ms→−0.03ms**となり、ドラッグ位置による差も消えた（2%地点で+0.09ms、75%地点で−0.46ms）
  - 折りたたみ機能そのものに手を入れる変更のため、畳む・展開する・すべてのコメントブロックを畳む・折りたたみレベルの指定・タブ切替後、のそれぞれで**実際に行が隠れること**を自動テストで確認している（マーカーを押している最中のフレームまで含めて検証）。設定項目は増えておらず、利用者から見た折りたたみの操作・見た目は一切変わらない
  - あわせて、構文強調が文字色のブラシと斜体の書体を**1トークンごとに毎フレーム作り直していた**のをやめ、テーマごとに1度だけ作って使い回すようにした。ただし正直に書くと、これ単体でのレイアウト時間の短縮は測定誤差の範囲だった（上乗せ+2.03ms→+2.00ms）。はっきり効いたのはメモリの割り当て量で、ドラッグ60ステップ分が116.6MB→110.9MB（1フレームあたり約95KB減）になっている。ドラッグ中のGCの圧力が下がる分、時間の中央値ではなく「時々出る引っかかり」に効く種類の改善である
  - 【副次的な効果】 本版で修正した課題#82（タブ切替時にまれに出る`Invalid document`の未処理例外）は、この`Invalid document`を投げる箇所がエディタ基盤の中で**折りたたみの描画部品ただ1箇所**しか無い。今回の変更により、**どこも畳んでいない通常状態ではその経路自体を通らなくなった**（1つでも畳んでいれば従来どおり通るため、1.0.13の対処はそのまま残してある）。この2つの状態の違いも自動テストで固定した
- 行の折り返しを有効にしているとき、折り返された2行目以降を、その行のインデント位置まで字下げして表示するようにした（課題#72）。深く字下げされたコードの長い行が折り返されると、続きが画面の左端から書き出されてしまい、どこからどこまでが1行なのか・どのブロックに属する行なのかが読み取りにくかった。今後は続きの行が元の行のインデント位置から始まるため、インデントガイド（縦線）とも重ならず、折り返しても構造が目で追える
  - 【なぜ今まで効かなかったか】 この動作はエディタ基盤（AvaloniaEdit）に`InheritWordWrapIndentation`（既定オン）という設定として最初から備わっているが、実際には一度も効いていなかった。原因は基盤側の2箇所にある。①AvaloniaEdit 11.1.0（Graftが性能要件のために固定しているバージョン。11.4.0でも未修正）は、行の書式を組み立てる際に「段落の1行目か」を示すフラグを設定し忘れており、字下げ量を計算するコード自体が一度も実行されない。②仮に①が直っても、その下のUI基盤（Avalonia 11.2.3、最新の11.3.20も同様）のテキスト整形器が、字下げ量を受け取るプロパティを一切参照していない。したがってGraft側で設定値を変えるだけでは実現できず、Graftが自前の整形器を挟む形で実装した（`src/Graft/Editor/WrapIndentSupport.cs`のコメントに、該当するクラス名・メソッド名・行番号まで含めた調査結果を残してある）
  - この実装はエディタ基盤の内部（非公開）に触れるため、将来基盤側の作りが変わって触れなくなった場合は、アプリを落とさずに「字下げが効かないだけ」の従来どおりの表示へ静かに戻る。その事実はログへ記録されるので、気付かないまま劣化し続けることはない（回帰テストで確認済み）
  - 右横書き（アラビア語・ヘブライ語など）を含む行では字下げを適用せず、従来どおりの表示にする。双方向テキストでは文字の並びが視覚的に入れ替わるため「行頭の空白の幅」を正しく測れず、誤った位置へ字下げするより従来どおりの方が安全なため
  - 設定項目は増やしていない（常時オン）。エディタ基盤でも既定でオンとされている動作であり、「1行として続いているものを1行として見せる」という表示の正しさに関わる挙動のため、利用者に選ばせる性質のものではないと判断した

### 修正
- 起動のたびに必ず走る起動時検証（back/配下の実体走査によるリビジョン番号の補正）が、その完了を待たずに他の操作（プロジェクトの登録・削除など）が行われた場合、古い一覧のスナップショットで上書きしてしまうことがある問題を修正した。「使い方を学ぶ」チュートリアル終了後にプロジェクトが一覧から消えるという報告の調査で見つけたもので、リビジョン番号の補正は対象プロジェクト1件だけを更新する方式に改め、他の操作の結果を巻き戻さないようにした
- 折りたたみ有効時にタブを切り替えると、まれに`System.ArgumentException: Invalid document`という未処理例外が発生する不具合（課題#82）の入口を特定し、修正した。過去2回（課題#60・PR #33）「修正済み」としていたが実機ログで再発しており、今回さらに一段深い原因を突き止めた
  - 【真因】 `Editor.Document`を新しい文書へ差し替える処理は、AvaloniaEdit内部で`TextArea.Document`→`TextView.Document`の順に**同期的に**伝播したあと、キャレット位置を(1,1)へリセットする（`Caret.PositionChanged`が同期発火する）。折りたたみの再接続（古い`FoldingManager`を外して新しい文書で作り直す処理）は、この一連の流れの中で**一番最後に**発火する`TextEditor.DocumentChanged`イベントを契機にしていた。つまり「`TextView`の文書は新しいが、`FoldingManager`は古い文書のまま」という食い違った状態が、キャレットのリセット中に一瞬存在していた。このキャレットのリセット中（`Caret.PositionChanged`発火中）にOSレベルの再入（Windows実機でのIME通知・フォーカス変更・アクセシビリティ通知等に伴うネイティブメッセージポンプの入れ子呼び出しが典型例）で保留中の描画パスが処理されると、この食い違った状態のままレイアウトが走り、`Invalid document`が投げられる。実機ログの3件が起動直後（タブ復元中、複数回連続してDocumentが差し替わるタイミング）に集中していたことと符合する
  - この機序は自動テスト（headless）でも実際に再現できることを確認した（`tests/Graft.UiTests/EditorTests.cs`の「課題#82入口特定」テスト。`Caret.PositionChanged`のハンドラ内で`Dispatcher.UIThread.RunJobs()`を呼び、実機のネイティブメッセージポンプ再入と同じ効果をプラットフォーム非依存に再現している）
  - 【対処】 `Editor.Document`へ代入する**前**に、古い`FoldingManager`を先回りして取り外す（`FoldingSupport.PrepareForDocumentSwap`）よう`EditorPane`（タブ切替・空タブ化の両経路）を直した。これにより代入中のどの瞬間に再入が起きても、`FoldingManager`が存在しない状態のため例外の温床そのものが無くなる。同じ再入を起こしても例外が出ないことを回帰テストで確認済み
  - 併せて、この不具合が実機で発生した際に握りつぶした（あるいは記録した）回数を、既存の集計の仕組み（PR #45の`SuppressedExceptionTracker`）にも乗せるようにした。今後同種の未処理例外が起きた場合、終了時ログの集計で発生種類・回数がすぐ分かるようになる

### その他
- 折りたたみ機能の回帰テストを大幅に増やした（自動テストは単体1029件・UI783件の計1812件になった）。スクロールバーのドラッグ改善（課題#73）が折りたたみの描画経路そのものに手を入れるものであるため、「畳む・展開する・すべてのコメントブロックを畳む・折りたたみレベルの指定・再帰的な折りたたみ・タブ切替後・設定での無効化と再有効化」のそれぞれで**実際に行が隠れるところまで**確認する。加えて、テーマを切り替えたときに構文強調の色が追従することも自動テストで固定した（今回入れた色のキャッシュが古い色を握り続ける退行を防ぐため）
- 自動テストに、**行の折り返しを有効にした状態**での10万行の性能計測（読み込みと初回描画・スクロール）を追加した。Graftの既定は折り返しオンであるにもかかわらず、これまでの性能テストはすべて折り返しオフのエディタで計測しており、利用者が実際に使う経路の性能が一度も守られていなかった。あわせて、計測が本当に折り返し経路を通っていること自体を確かめる番人も入れた（幅やフォントの変更で折り返らなくなると、テストは通るのに何も守らない状態になるため）
- 仕様書（`docs/仕様書_Graft_v2.1.md`）を実装の実態に合わせて更新した。データ保存先の選択・Gitの自動コミット・エラー詳細のコピー・ログ参照・キーボードショートカットの追加など、既に実装済みだが記載が漏れていた機能を反映し、エラーコード表とテスト件数（自動テスト1708件）も実測値へ更新した。利用者への直接の影響は無い

## 1.0.12

### 改善
- 「起動時に更新を確認する」をオンにしていても、実際には前回の確認から24時間経つまで起動時の確認が行われず、チェックボックスの文言と動作が食い違っていた（利用者からの指摘）。今後は文言どおり、Graftを起動するたびに必ず確認する
- ただし、テーマ変更・データ保存先の移動・自動更新の適用後などGraft自身が再起動して立ち上がったときは、この「起動のたびに確認する」の対象から除いた。「起動のたびに確認する」のはあくまで利用者が自分の意思でGraftを起動したときの話であり、Graftの都合による再起動のたびにまで確認しに行く必要は無いため
- 自動更新のダウンロード中にGraftが強制終了・クラッシュすると、ダウンロード中だった一時ファイル（50MB超のZIPを含む一時作業フォルダ）がそのまま残り続け、次回以降も一切掃除されない不具合を修正した。今後は次回起動時に、作成から24時間以上経過した古い一時作業フォルダだけを自動的に削除する（実行中の更新を誤って削除しないための猶予時間）。また、更新を1回試みるたびに空の一時フォルダが1つずつ残り続けていた不具合もあわせて修正した

## 1.0.11

### 修正
- 自動更新に成功したあと、実行ファイルのフォルダに残る退避ファイル（`Graft.exe.old`等）が、「設定画面からデータ保存先をユーザーフォルダへ移動」している環境ではいつまで経っても掃除されず、更新のたびに積み上がっていく不具合を修正した。次回起動時の掃除処理が、退避ファイルの実際の置き場所（実行ファイルのフォルダ）ではなく設定・履歴等の保存先（データ保存先）を見に行っていたのが原因で、1.0.9で修正した自動更新のインストール先の取り違えと同じ種類の誤りが、この掃除処理だけ直っていなかった。ポータブル運用（データ保存先を移動していない環境）では両者が同じ場所のため、この不具合は発生しない

### 改善
- 「バージョン情報」タブに、更新を最後に確認した日時（「最終確認: yyyy/MM/dd HH:mm」、未確認なら「未確認」）を常時表示するようにした。起動時の確認は最新版のときに画面上へ何も表示されないため、確認したのか・24時間以内のため確認をスキップしたのか・そもそも確認できていないのかを見分けられなかった。あわせて、起動時・「今すぐ更新を確認」いずれの結果（最新だった・新版が見つかった・24時間未満のためスキップ・設定オフのためスキップ・通信に失敗）もログへ記録するようにした
- 「バージョン情報」タブの「チェック先URL」の入力欄を、ラベルの隣ではなくラベルの直下、「今すぐ更新を確認」ボタンの上に配置し直した。ラベル→入力欄→ボタンの縦並びにすることで対応関係が分かりやすくなり、入力欄もパネルの幅いっぱいまで使えるようになった

## 1.0.9

### 修正
- 設定画面から「データ保存先をユーザーフォルダへ移動」している場合、自動更新が必ず「ファイルの置き換えに失敗しました。Graft.exe を退避できませんでした」というエラーで失敗する不具合を修正した。自動更新が実行ファイルを置き換える場所と、settings.json等を保存する場所（データ保存先）を取り違えており、両者を別のフォルダにしている環境でだけ、実際には存在しないフォルダのGraft.exeを退避しようとして必ず失敗していた。ポータブル運用（データ保存先を移動していない環境）では両者が同じ場所のため、この不具合は発生しない

## 1.0.8

### 追加
- **自動更新機能を追加した。** 起動時（前回の確認から24時間以上経っていれば）と、設定「一般」タブの「今すぐ更新を確認」で、GitHubの公開リリースに新しいバージョンが無いか確認する。見つかった場合はダイアログで知らせ、同意した場合のみダウンロード・検証（SHA256）・置き換えを行い、確認のうえ再起動して反映する。書き込みが制限された場所（Program Files等）に置いている場合は自動更新をあきらめ、手動更新のためリリースページを開く案内を表示する。settings.json・プロジェクト一覧・バックアップ・ログ等、利用者のデータには一切触れない。設定「一般」タブで、起動時に確認するかどうか（既定オン）・チェック先URLを変更できる。確認・ダウンロードのとき以外、Graftは外部と通信しない（詳しい使い方は取扱説明書「更新」を参照）

### 修正
- AIの回答をコピーしやすいよう1つのコードブロックで丸ごと囲んで出力させたとき、パッチの中身自体に「```」を含む変更（Markdownファイルの編集など）を取り込むと、その```の行だけが黙って消えたまま適用されてしまう不具合を修正した（1.0.5から未修正のまま残っていた）。今後は囲み全体の外側だけを正しく見分けて取り除き、本文中の```はそのまま残す
- 上記に関連し、AIが指示文どおりに出力せず、本文の```と外側の囲みが衝突してしまい、囲みが途中で終わったと判断せざるを得ない場合は、黙って中身が欠けたまま取り込むのではなく、「パッチ本文に ``` が含まれているため、囲みが途中で閉じられた可能性があります」と案内し、書き直しを促すようにした

## 1.0.7

### 変更
- 設定「適用モード」の既定を「全件適用（All or Nothing）」から「部分適用可」に変更した。AIの回答の一部だけが実際のコードに当てはまらないのはよくあることで、これまでは既定のままだと、当てはまった変更が残っているにもかかわらず適用そのものがエラーになり、履歴にも記録されなかった。今後は既定のまま、当てはまった変更はきちんと適用されて履歴に残り、「元に戻す」もできる。当てはまらなかった変更があったことは、完了メッセージに件数を添えて知らせる。なお、すでに「全件適用」を選んでいる方の設定はそのまま引き継がれ、勝手に変わることはない

### 改善
- うまく動かないときの原因を調べやすくするため、起動時とプロジェクトを切り替えたときに、動作環境の要約（プロジェクトの場所・保存先・取り込みの挙動に関わる設定）をログへ記録するようにした
- 画面には出ないごく小さな不具合が裏側で繰り返し起きていないかを終了時のログから確認できるよう、発生回数の集計を記録するようにした（1度も起きていないものは表示されない）

### 修正
- ネットワーク上（共有フォルダ）に置いたプロジェクトを取り込むと、すべてのブロックが必ず失敗する不具合を修正した。プロジェクトの場所を記録した情報が壊れた形で保存されてしまい、まったく関係のない場所（Graftを起動したフォルダの中）を探しに行ってしまうことがあった。すでにこの状態で登録されているプロジェクトも、次に開いたときに自動的に直る
- 上記と合わせて、プロジェクトの場所を新しく登録・変更するときにも同じ壊れ方をしないよう防止策を加えた
- 「全件適用」を選んでいるときに一部の変更が当てはまらず中止した場合、これまでは中止した理由（設定によるもの）が伝わらず、原因不明のエラーのように見えてしまっていた。今後は「『全件適用』の設定のため中止しました。『部分適用可』に切り替えると、適用できる変更だけを書き込めます」という案内を表示し、個々の変更のエラーもあわせて示す
- 適用できる変更のチェックを画面上ですべて外した状態で「適用」を押すと、何も変更していないのに履歴だけが1件増えてしまう不具合を修正した。今後は「適用対象がありません」という案内を表示し、履歴は増やさない
- ファイルへの取り込み直後や、外部でファイルが書き換わった直後など、ファイルを読み込み直すタイミングで、まれにアプリが停止することがある不具合を修正した
- 折りたたみマーカー（コード左端に出る＋－の四角いボタン）が、環境によっては中の＋－がほとんど見えず、ただの塗りつぶした四角に見えてしまう不具合を修正した。9種類あるすべてのテーマで＋－がはっきり読めるようにした

## 1.0.6

### 追加
- 検索（Ctrl+F）でヒットした文字を見やすくした。一致した箇所には枠線付きの色を付け、いま選んでいる箇所は色も枠線も一段と目立つようにした。すべてのテーマで、色が見分けにくくても枠線の太さで現在地が分かる
- コードエディタのスクロールバーに、検索結果が文書全体のどのあたりにあるかを示す小さな目印を表示するようにした

### 改善
- 対象のファイルが見つからない・読み取れない場合に、専用のエラー（E210）で知らせるようにした。従来は「SEARCH部が見つからない」と表示され、原因が分かりにくかった。メッセージには Graft が実際に確認した絶対パスを添える
- 解析（ドライラン）のときに、対象ファイルごとの「絶対パス・存在の有無・行数」をログへ記録するようにした。うまく取り込めないときの原因調査に使える
- 長いパス用の内部処理を見直し、必要な長さのときだけ特殊な形式のパスを使うようにした（ネットワークドライブ上での不確実性に対する予防）

### 修正
- ファイルやフォルダを新しく作った直後に、ツリー上で自動的に選ばれないことがある不具合を修正した（自分自身の書き込みをファイル監視が拾ってしまう順序の問題）

## 1.0.3

### 追加
- テーマを9種類から選べるようにした（ライト／ダークに加え、セピア・GitHub・Solarized Light／Dark・Nord・Dracula・ナイト）
- 本文と等幅の書体を、それぞれ設定から選べるようにした
- インデントガイド（字下げの位置を示す縦線）を追加した。「表示しない」「折りたたみできる範囲のみ」「すべての字下げ」から選べる
- 折りたたみを拡張した。マーカーにマウスを乗せると対応する範囲が強調され、「すべて折りたたむ」「すべて展開する」「コメントをまとめて折りたたむ」をコマンドパレットから実行できる
- コードの中の色（`#RRGGBB`・`rgb()`・`hsl()`）の手前に色見本を表示し、クリックすると色を選び直せるようにした。書き換えても元の書き方（大文字小文字・桁数・区切り方）はそのまま保たれる
- Markdownの編集を補助するようにした。リストや引用はEnterで続きが作られ、空のままEnterを押すと抜けられる。表の中ではTabとShift+Tabでセルを移動でき、最後のセルでEnterを押すと行が増える
- ツールチップの詳しさを4段階（詳しい／ふつう／最低限／表示しない）から選べるようにした

### 改善
- 折りたたみマーカーから伸びていた縦線と横線（L字の線）を表示しないようにした
- 折りたたみマーカーの左右の余白を広げ、左右対称にした
- 行番号や折りたたみの帯の上では、マウスカーソルが矢印になるようにした（従来は文字入力用の形のままだった）

### 修正
- Markdownプレビューで、コードブロックや表に横スクロールバーが出たとき、最後の行に重なって読めなくなる不具合を修正した
- 折りたたみマーカーにマウスを乗せたとき、縦線の強調がちらつく不具合を修正した。あわせて、カーソルを動かすたびに画面全体のレイアウトを計算し直していた無駄も解消した
- ファイルの削除を続けて行ったとき、ごく稀にアプリが停止することがある不具合を修正した（削除の取り消し用の記録が、複数の処理から同時に書き換えられていた）
