# リリース手順

Graftの配布物（Windows版のZIPとLinux版のtar.gz）を作成し、GitHub Releaseとして公開するまでの
手順です。リリースは **`.github/workflows/release.yml`（Actionsの「リリース」）が正規の経路**で、
`v` で始まるタグをpushすると、テスト・発行・書庫の作成と中身の確認・リリース本文の組み立てまでを
Linuxランナー上で行い、GitHub Releaseを**下書き**として作ります。人が行うのは、タグのpushと、
下書きを確かめて「Publish」を押すことだけです。

`tools\New-Release.ps1` で書庫を作って手で添付する従来の手作業は、リリースの経路としては
使いません（手元で試すための道具として残してあります。下の「手元で試すとき」参照）。

## 手順

1. **`main` を最新にして、出したい版になっているか確かめる**

   `src\Graft\Graft.csproj` の `<Version>` が出したい版であることを確認します。
   タグと `<Version>` が食い違うと、ワークフローは「版の確認」で止まります。

   ```powershell
   cd C:\Users\YUGO\Graft
   git checkout main
   git pull origin main
   Select-String -Path src\Graft\Graft.csproj -Pattern '<Version>'
   ```

2. **タグを作ってpushする（これでワークフローが走る）**

   ```powershell
   cd C:\Users\YUGO\Graft
   git tag -a v<バージョン> -m "Graft <バージョン>"
   git push origin v<バージョン>
   ```

   タグは `v1.2.3` の形にします（自動更新が解釈できる形。下の「バージョン表記は3点区切り」参照）。

3. **Actionsの「リリース」の進行を確かめる**

   [Actions](https://github.com/Yu5rin/Graft/actions) を開き、「リリース」が次の順に進んで
   緑になることを確認します。

   テスト → 版の確認 → 発行（Windows・Linux） → 同梱物を置く → 配布物をまとめる →
   配布物の中身を確かめる → リリース本文を組み立てる → リリースを作成（下書き）

   途中で赤くなったら、下書きは作られません。ログの該当の段を読んで原因を直します。

4. **作られた下書きを確かめて「Publish」を押す**

   [Releases](https://github.com/Yu5rin/Graft/releases) に「Draft」として現れるリリースを開き、
   次を確かめてから公開します。公開は人が押す決まりです（ワークフローは `draft: true` で作ります）。

   - 添付が2件ある: `Graft-<バージョン>-win-x64.zip` と `Graft-<バージョン>-linux-x64.tar.gz`
   - タイトルがタグと同じ `v<バージョン>` になっている（「Graft 1.0.20」のような書き方はしない）
   - 本文が `## 変更点` と `## ダウンロード` の2節だけで、最後に README への案内が1行ある
   - 変更点が、その版の分だけ、利用者向けの日本語で書かれている
   - ダウンロード表のファイル名・サイズ・SHA256 が、添付と合っている
     （表はワークフローが添付した書庫そのものから計算するので、通常は食い違いません）

---

## 手元で試すとき

リリースには使いませんが、書庫の中身や同梱物を手元（Windows）で確かめたいときは、
`tools\New-Release.ps1` が使えます。ビルド・同梱物の配置・書庫の作成・検証までを1コマンドで行います。

```powershell
cd C:\Users\YUGO\Graft
powershell -ExecutionPolicy Bypass -File tools\New-Release.ps1
```

既定では `src\Graft\Graft.csproj` の `<Version>` からバージョンを算出し、`publish\release\Graft`
へ発行したうえで、リポジトリ直下に `Graft-<バージョン>-win-x64.zip` と
`Graft-<バージョン>-linux-x64.tar.gz` を作成します。Windows上からでもLinux版を
発行できます（.NETがクロスOSの発行に対応しているため）。作業ツリーが汚れている場合は
警告して中断します（問題なければ `-Force` を付けて再実行してください）。

- 書庫: リポジトリ直下の `Graft-<バージョン>-win-x64.zip` / `Graft-<バージョン>-linux-x64.tar.gz`
- 本文の下書き: `publish\release\リリース説明.md`
  （`docs\リリース説明_テンプレート.md` に、`docs\変更履歴.md` の該当する版の節と、
  書庫のファイル名・サイズ・SHA256の表を差し込んだものです）
- スクリプトが表示する「ZIPの中身一覧」「tar.gzの中身」「`Graft.exe` のファイルバージョン」

**ここで作った書庫や本文を、GitHub Releaseへ添付・貼り付けて公開しないでください。**
手元で作った書庫は、ワークフローが作る書庫とバイト単位で一致しません（Windowsで作るとtar.gzの
実行権限が落ちる、など）。本文の表のSHA256を手で貼ると食い違いの元になります
（下の「ダウンロード表のSHA256は手で書かない」参照）。

## 注意点

### リリース本文は「変更点」と「ダウンロード」だけ

リリース本文に置く見出しは `## 変更点` と `## ダウンロード` の2つだけにし、その版の変更の
小見出しは `###` 以下にします。本文に「# Graft 1.0.20」のような題名は書きません。
インストール・更新の方法、主な機能、動作環境、外部との通信、既知の制限などの版をまたいで
変わらない説明は README に置き、リリース本文には繰り返しません（本文の最後に README への
案内を1行置きます）。その版へ上げるときだけ必要な注意（手で入れ替える必要がある等）は、
`### ` の小見出しとして変更点の中に書きます。

### バージョン表記は3点区切り（例: `1.0.1`）

ZIP名・タグ・`はじめにお読みください.txt`・リリース説明.md等、利用者向けの表記は
`src\Graft\Graft.csproj` の `<Version>` の値をそのまま使います（桁を補いません）。
**`v1.0.0.0` / `Graft-1.0.0.0-win-x64.zip` だけは例外**で、最初のリリースを実際に4点区切り
（`v1.0.0.0`）で公開してしまった経緯により、過去の実物に合わせてそのままにしています。
`1.0.1` 以降は3点区切りが基本です。

### 発行先は `publish\Graft` とは別

`tools\New-Release.ps1` の発行先は既定で **`publish\release\Graft`** です。これは利用者が普段
使う **`publish\Graft`（README「発行」節の手順で作る場所）とは別のフォルダ**です。

`tools\New-Release.ps1` は実行前に発行先フォルダを削除してから発行し直します。誤って
`publish\Graft` を発行先に指定すると、そこに置いてある `settings.json` / `projects.json` /
`back/`（バックアップ）/ `logs/` が消えてしまいます。過去に実際、利用者へ「`publish\Graft` を
消してからpublishする」という手順を案内してしまい、設定・履歴・バックアップを毎回失わせる
という迷惑をかけたことがあります。同じ事故を防ぐため、スクリプト側でも `publish\Graft` を
発行先に指定した場合は `-Force` を付けても中断するようにしています。

### ダウンロード表のSHA256は手で書かない

リリース本文の「## ダウンロード」の表（ファイル名・サイズ・SHA256）は、**ワークフローが、
添付する書庫そのものから `stat -c %s` と `sha256sum` で計算して**組み立てます。
手で書いたり、別の環境（手元のWindowsなど）でビルドした書庫のハッシュを貼ったりしないでください。

v1.0.22で実際に、本文の表のSHA256が、添付した書庫と一致しない事故が起きました。別の環境で
ビルドした書庫のハッシュを手で貼ってしまったためです。自動更新はリリース本文を読まず、
API の添付の `digest` を使うので更新は壊れませんでしたが、本文のSHA256で検証した人には
「ファイルが壊れている」と見えます。ワークフローに一本化したのは、この混入経路を無くすためです。
本文を直したいときは、表には触れず、「## 変更点」の部分だけを下書きの上で直します。

### Linux版のtar.gzの実行権限

Linux版をzipではなくtar.gzにしているのは、zipがUnixのファイル属性を持てず実行権限が
失われるためです。ワークフローは**Linuxランナー上でtar.gzを作る**ので、実行権限は保たれます。
一方、`tools\New-Release.ps1` を**Windows上で動かして作ったtar.gzは、実行権限が落ちることがあります**
（NTFSにUnixのファイル属性が無いため。v1.0.20の実物でも確認しています）。そのため同梱の
`はじめにお読みください.txt` には、権限が付いていない場合に備えて、常に `chmod +x Graft` の
案内を載せてあります。

### `.github/workflows/release.yml` はタグpushで発火する（手作業と二重に走らせない）

`release.yml` は、`v` で始まるタグをpushすると自動で発火します（Actions画面からの手動実行
`workflow_dispatch` も残してあり、タグを選んで再実行できます）。ブランチ（`main` 等）を選んで
実行すると、「版の確認」で止まります（添付名がタグから決まるため。これは意図した挙動です）。

かつては、`workflow_dispatch` のみにしていました。`v1.0.1` で、タグpushによる自動発火と
`tools\New-Release.ps1` による手作業のリリースが二重に動き、同じ版の書庫が複数並んで公開される
事故が起きたためです（`Graft-1.0.1-win-x64.zip` と `Graft-v1.0.1-win-x64.zip`・
`Graft-v1.0.1-linux-x64.tar.gz` が同じリリースに混在してしまいました）。

いまタグpushで発火させているのは、リリースの経路をワークフローに一本化したからです。
二重発火が事故になったのは手作業の経路を併用していたからで、一本化すればその原因は無くなります。
また添付名は `tools\New-Release.ps1` と同じ規則（`Graft-<バージョン>-win-x64.zip`、先頭の `v` なし）に
揃えてあるので、仮に両方が動いても、名前の食い違う書庫が並ぶ形にはなりません。
ただし**二重に走らせないこと自体は今も方針**です。タグをpushしたら、手作業で書庫を作って
同じリリースへ添付する経路は使わないでください。

### コード署名をしていない

Graftにはコード署名証明書を付けていません。配布したZIPを展開して `Graft.exe` を実行すると、
Windowsの SmartScreen が「WindowsによってPCが保護されました」という警告を表示します。
これは異常ではなく、内容を確認のうえ「詳細情報」→「実行」で起動できます。
（`はじめにお読みください.txt` にも同じ案内を同梱しています。）

### `datapath.txt` とフォルダの差し替え

保存先をユーザーフォルダ（`%APPDATA%\Graft`）へ移した利用者の環境では、実際の保存先を指す
`datapath.txt` が `Graft.exe` と同じフォルダに置かれます。新しい版のフォルダへ差し替える際に
この `datapath.txt` ごと入れ替えてしまっても、Graftは起動時に「以前ユーザーフォルダに保存した
データが見つかりました」と復帰確認ダイアログを出すため、そこで「はい」を選べば設定・履歴・
バックアップを失わずに済みます（詳細は `docs\取扱説明書.md` の「データの保存場所」章を参照）。
